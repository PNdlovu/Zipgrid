## 1. Definition of Done (DoD)

A feature is done when ALL of the following are true. Not some. All.

```
CODE
  □ All business logic has unit tests (TDD — tests written first)
  □ All API routes have Zod validation schemas
  □ All API routes have auth middleware applied
  □ All API routes return the standard response envelope
  □ No TypeScript any or ts-ignore used
  □ No hardcoded strings — all user-facing text in i18n files
  □ All monetary values stored as integers (pence)
  □ JSDoc header on every new file
  □ No cross-domain internal imports
  □ No stubs, no mocks, no TODO comments in production code

UI
  □ Renders correctly in all 3 themes (Light / Dark / Night)
  □ All interactive elements have working onClick handlers
  □ Loading states implemented (skeleton or spinner as appropriate)
  □ Empty state implemented
  □ Error state implemented (via error boundary)
  □ Offline fallback implemented where relevant
  □ All touch targets ≥ 44px
  □ Keyboard-navigable
  □ Screen reader tested (manual or axe-core)

TESTS
  □ Unit tests: new business logic at ≥ 95% coverage
  □ Component tests: key interactions tested with RTL
  □ E2E test: happy path + at least one error path
  □ Accessibility: axe-core passes with zero violations
  □ Tests pass in all 3 environments (dev / staging / prod)

DATA
  □ New DB tables have a migration file (not hand-edited schema)
  □ Migration is backward-compatible
  □ Seed data updated if new tables were added
  □ All new list queries are paginated

DOCUMENTATION
  □ API endpoint documented in 3.3-api-specification.md
  □ If new domain concept: updated in relevant design doc
  □ New voice commands added to 2.10-voice-navigation-system.md
  □ PR description links to Linear ticket

REVIEW
  □ At least 1 peer review approved
  □ No outstanding review comments
  □ CI checks pass (when enabled)
  □ Screenshots/videos of UI change (all 3 themes) attached to PR
```

## 2. Acceptance Criteria Format

Every feature ticket in Linear must have explicit acceptance criteria using the Gherkin format. This format is unambiguous and directly maps to automated tests.

### Format

```
GIVEN [precondition — the state of the world before the action]
WHEN  [action — what the user does]
THEN  [expected outcome — what must be true after]
AND   [additional expected outcome]
```

### Examples

**BOOK-001: Driver creates a booking**

```gherkin
GIVEN the driver is logged in with a verified email
AND the driver has at least one vehicle registered
AND the listing "Sarah's Earlsfield Driveway" is active and available on 2027-01-06 at 10:00
WHEN the driver selects the listing and picks the 10:00–12:00 slot
AND the driver selects their primary vehicle (Tesla Model 3)
AND the driver taps "Confirm Booking" with a valid saved card
THEN a booking is created with status "confirmed"
AND a Stripe PaymentIntent is created with status "requires_capture"
AND the driver sees a confirmation screen with a QR code and 6-digit PIN
AND a push notification "Booking confirmed" is sent to the driver
AND a push notification "New booking" is sent to the host
AND the booking appears in the driver's booking history

GIVEN the same listing and slot
WHEN a second driver attempts to book the same slot
THEN the booking is rejected with error "BOOKING_OVERLAP"
AND no PaymentIntent is created
```

**SESS-003: Real-time kWh update**

```gherkin
GIVEN an active charging session exists (status: "charging")
AND the charger sends a MeterValues OCPP message with energyWh = 5200
WHEN the OCPP service processes the message
THEN the session_meter_values table has a new row with energy_wh = 5200
AND the driver's active session screen updates within 5 seconds
AND the displayed kWh shows 5.2 kWh
AND the displayed cost updates based on the per-kWh rate

GIVEN the same session
AND the driver's app is in offline mode
WHEN the OCPP service processes a new MeterValues message
THEN the session screen shows "Updates paused — offline" banner
AND the last-known values remain displayed
AND when the driver reconnects, the screen updates within 5 seconds
```

**VOICE-005: Book by voice command**

```gherkin
GIVEN the driver is on the map screen
AND Hybrid mode is active
AND the driver has at least one compatible listing within 1 mile
WHEN the driver says "Book the nearest CCS charger for tomorrow at 10am"
THEN the AI parses intent: book_charger with plugType=CCS2, date=tomorrow, time=10:00
AND a confirmation overlay appears: "Book [listing name] tomorrow at 10am, est. £5.40?"
AND two buttons are shown: "Yes, book it" and "Not now"
WHEN the driver says "Yes" or taps "Yes, book it"
THEN a booking is created as per BOOK-001 acceptance criteria
AND the voice assistant responds: "Done. [Listing name], tomorrow 10am. Code: ZG-XXXX"
```

## 4. No Partial Features Rule

A feature enters production in one of two states:

```
STATE A: Complete
  - All DoD checkboxes satisfied
  - All AC scenarios pass
  - All 3 themes work
  - Tests passing
  → SHIPS

STATE B: Not started / In development
  - Feature flag is OFF in production
  - Code may exist but is not reachable by users
  - No placeholder UI visible
  → DOES NOT SHIP until STATE A
```

**There is no STATE C** (partial implementation, placeholder button, "coming soon" screen). If it is not done, users do not see it.

The only exception: a well-designed empty state on a screen that exists but has no data yet. Empty states are real UX — they are not placeholders.

## 5. Feature Flag System

PostHog feature flags control which features are live in production. This allows code to be deployed without activating the feature for users.

```typescript
/**
 * Usage in components:
 * const { isEnabled } = useFeatureFlag('wallet-topup')
 * if (!isEnabled) return null
 *
 * Usage in API routes:
 * const flagEnabled = await checkFeatureFlag('wallet-topup', userId)
 * if (!flagEnabled) return apiError('FEATURE_NOT_AVAILABLE', 404)
 */
```

Every new Phase 2+ feature gets a feature flag at creation. This means:
- Code ships with flag OFF
- QA and testing happen with flag ON for test accounts
- Feature goes live when flag turned ON for all users
- Feature can be instantly turned OFF if a problem is found — no rollback needed
