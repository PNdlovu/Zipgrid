## 1. Architecture Overview

Zipgrid is built as a **service-oriented monorepo** — a single Next.js 15 application handling the web/app frontend and API routes, backed by purpose-built standalone services for OCPP (real-time charger communication) and AI/voice (LangChain agentic layer). This avoids premature microservice complexity while keeping critical real-time and AI workloads isolated for independent scaling.

## 2. Core Service Breakdown

### 2.1 Next.js 15 Application (Primary)

**Responsibilities:**
- All user-facing UI (driver app, host portal, SMB dashboard, admin panel, marketplace)
- API routes (`/api/v1/*`) for mobile clients and third-party integrations
- Server Actions for form submissions and mutations (reduces client-server round trips)
- React Server Components for SEO-critical pages (listing pages, marketplace, knowledge base)
- Authentication middleware (JWT validation on every request)
- Webhook receivers (Stripe, OCPP service events)

**Deployment:** Vercel (Edge Network for static + CDN assets; Serverless Functions for API routes)

**Key Next.js patterns:**
```
app/
├── (auth)/              — login, register, verify, reset
├── (driver)/            — map search, listing detail, booking, session
├── (host)/              — dashboard, listings, availability, earnings
├── (smb)/               — multi-charger dashboard, analytics, access control
├── (marketplace)/       — hardware shop, installer profiles, community
├── (admin)/             — platform ops, moderation, disputes
├── api/
│   ├── v1/
│   │   ├── auth/        — JWT issue/refresh
│   │   ├── listings/    — CRUD + geo-search
│   │   ├── bookings/    — create/confirm/cancel
│   │   ├── sessions/    — start/stop/status
│   │   ├── payments/    — Stripe webhooks
│   │   ├── voice/       — STT → intent → response
│   │   └── ai/          — agentic workflow triggers
│   └── webhooks/
│       ├── stripe/
│       └── ocpp/
└── middleware.ts        — auth guard, rate limit, logging
```

### 2.2 OCPP WebSocket Service (Standalone)

**Technology:** Node.js + `ws` library + custom OCPP 1.6J/2.0.1 Central System implementation

**Why standalone:** WebSocket connections are long-lived (hours per charging session). Vercel Serverless Functions have a maximum execution time, making them unsuitable. A persistent Node.js process on Railway or Render handles all charger connections.

**Deployment:** Railway (persistent service, auto-restart, health checks)

**Architecture:**
```
┌─────────────────────────────────────────────────────────┐
│                OCPP Central System                      │
│                                                         │
│  ┌─────────────────┐    ┌──────────────────────────┐   │
│  │  Connection     │    │  Message Router           │   │
│  │  Manager        │    │                           │   │
│  │                 │    │  BootNotification     →   │   │
│  │  Map:           │    │  Authorize            →   │   │
│  │  cpId → WS conn │    │  StartTransaction     →   │   │
│  │                 │    │  StopTransaction      →   │   │
│  └────────┬────────┘    │  MeterValues          →   │   │
│           │             │  StatusNotification   →   │   │
│           │             │  Heartbeat            →   │   │
│           │             └──────────┬───────────────┘   │
│           │                        │                   │
│           │             ┌──────────▼───────────────┐   │
│           │             │  Event Publisher          │   │
│           │             │                           │   │
│           │             │  → PostgreSQL (persist)   │   │
│           │             │  → Redis pub/sub          │   │
│           │             │    (real-time to app)     │   │
│           │             │  → Webhook to Next.js API │   │
│           │             └───────────────────────────┘   │
│                                                         │
│  Inbound commands from Next.js API:                     │

│  POST /ocpp/remote-stop   { cpId, transactionId }       │
└─────────────────────────────────────────────────────────┘
```

**Real-time telemetry flow:**
```
Charger → MeterValues OCPP message
       → OCPP Service processes
       → Publishes to Redis channel: session:{sessionId}:meters
       → Next.js Supabase Realtime subscription OR
         Pusher channel pushed to driver app WebSocket

```

### 2.3 AI / Voice Service (Standalone)

**Technology:** Python FastAPI + LangChain + OpenAI + Pinecone

**Why Python:** LangChain, LlamaIndex, and the broader AI/ML ecosystem are Python-native. Running AI in a dedicated Python service avoids forcing Node.js to handle heavy inference orchestration.

**Why standalone:** LLM calls are high-latency (1–4 seconds). Isolating them prevents slow AI responses from blocking fast API routes in the Next.js service.

**Deployment:** Railway (persistent, GPU-optional for Whisper local inference at scale)


**Voice request flow:**
```
1. User speaks into mic (iOS/Android/Web)
2. Browser Web Speech API → text transcript (instant, free)
   OR audio blob sent to POST /voice/transcribe → Whisper API
3. Text sent to POST /voice/intent → GPT-4o parses intent
   e.g. { intent: "book_charger", entities: { location: "Clapham", time: "tomorrow 10am", duration: 2 } }
4. If intent requires action → POST /agent/run → LangChain agent executes
5. Agent calls tool(s) → e.g. search_listings() → create_booking()
6. Agent returns structured response
7. Response text converted to speech (Web Speech Synthesis or ElevenLabs)
8. Spoken + displayed to user simultaneously
```

## 3. Database Architecture

### Primary: PostgreSQL 16 + PostGIS (Supabase)

Full schema documented in `db/migrations/`. Key design decisions:
- All monetary values in **pence (INT)** — no floats
- Spatial columns use **GEOGRAPHY(POINT, 4326)** — metres-based distance queries
- GIST index on `charger_listings.location` — radius searches are index scans
- GIN index on `plug_types[]` and `amenity_tags[]` — array overlap queries
- OCPP meter values use **BIGSERIAL** PK — high-frequency insert throughput
- Audit log is **append-only** (REVOKE UPDATE/DELETE on `audit_log` from app role)

### Cache: Redis (Upstash — serverless Redis)

| Key Pattern | TTL | Purpose |
|-------------|-----|---------|
| `session:{id}:meters` | 5 min | Latest MeterValues for active session |
| `listing:{id}:availability` | 15 min | Cached availability calendar |
| `tariff:octopus:agile:{date}` | 1 hr | Octopus Agile half-hourly rates |
| `user:{id}:preferences` | 1 hr | Voice/AI user preferences |
| `geo:pins:{bbox_hash}` | 5 min | Map pin cluster cache |
| `ratelimit:{ip}:{endpoint}` | 1 min | API rate limiting counters |

### Realtime: Supabase Realtime

Used for pushing OCPP session telemetry from the OCPP service → Next.js app → driver browser/mobile:
```
OCPP Service → Redis pub/sub → Supabase Realtime listener →
WebSocket channel: session:{sessionId} →
Driver app updates kWh display in < 5 seconds
```

## 4. Authentication & Security

### Auth Flow
```
Registration → Email verify → JWT issued (15min access + 7day refresh)
OAuth (Google/Apple) → JWT issued same way
All API requests → middleware validates JWT → user context injected
Stripe Identity KYC → webhook updates users.kyc_status → hosting/selling unlocked
```

### Security Layers

| Layer | Implementation |
|-------|---------------|
| **Transport** | TLS 1.3 everywhere. HTTPS enforced. WSS for OCPP. |
| **Authentication** | JWT (HS256 access tokens, RS256 refresh tokens) |
| **Authorisation** | Row-Level Security (RLS) on Supabase — users can only read/write their own data |
| **Payment data** | Never touches Zipgrid servers — Stripe handles all card data (PCI-DSS SAQ A) |
| **PII encryption** | Access instructions (gate codes) AES-256 encrypted at rest |
| **Input validation** | Zod schema validation on all API inputs |
| **Rate limiting** | Upstash Redis-based rate limiting on all API routes |
| **OCPP security** | Basic Auth on OCPP WebSocket URLs; OCPP 2.0.1 adds TLS + certificate-based auth |
| **Secrets** | Vercel Environment Variables + Railway secrets — never in source code |
| **GDPR** | UK GDPR compliant: consent management, right to erasure, data export endpoint |
| **SOC 2** | Target Type I within 12 months — Vanta for compliance automation |

## 5. API Design

### Conventions
- **REST** for all CRUD operations
- **WebSocket** (Supabase Realtime / Pusher) for session telemetry
- **Server Actions** (Next.js) for form mutations — avoids extra API round-trip
- Versioned: `/api/v1/` — never break existing mobile app clients
- JSON responses with consistent envelope:

```json
{
  "success": true,
  "data": { ... },
  "error": null,
  "meta": { "page": 1, "total": 42 }
}
```

```yaml

  3. Run unit tests (Vitest)
```

### Alerting Thresholds

| Alert | Threshold | Action |
|-------|-----------|--------|
| API error rate | > 1% of requests | Page on-call engineer |
| OCPP service down | > 30 seconds offline | Auto-restart + alert |
| DB connection pool > 80% | > 80% utilisation | Scale read replica |
| Failed payments | > 5% failure rate | Alert payments team |
| Session stuck (no StopTransaction) | > 2hr past scheduled end | Auto-flag for ops review |
