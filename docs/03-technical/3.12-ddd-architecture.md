| Field | Value |
|-------|-------|

## 1. Why DDD for Zipgrid

Zipgrid is not a simple CRUD app. It operates across multiple distinct domains that each have their own:
- Business rules (charging pricing ≠ marketplace pricing)
- Data models (session data ≠ product data)
- External integrations (OCPP chargers ≠ Stripe payments)
- Regional variations (UK tariffs ≠ EU tariffs ≠ US tariffs)

Without domain separation, these concerns bleed into each other. Within six months you have charging logic in the payment module, marketplace rules in the booking module, and a codebase nobody can reason about.

**DDD solves this** by drawing explicit boundaries between domains. Each domain owns its own data, its own logic, and its own API contracts. Domains communicate only through well-defined interfaces — never by directly importing each other's internals.

**The migration path:**
```
Phase 1 — Modular Monolith:    One repo, one deployment, domain modules
Phase 2 — SOA:                 One repo, multiple services (separate Railway processes)
Phase 3 — Microservices:       Multiple repos, multiple deployments, independent DBs
```

You can split any module into a microservice without touching other modules — because the boundaries are already clean.

## 3. Domain Rules

### Rule 1: Domains Do Not Import Each Other's Internals

```typescript
// ✅ CORRECT — communicate through domain service interfaces
import { BookingService } from '@/domains/booking/BookingService'
const booking = await bookingService.create(params)

// ❌ WRONG — never import from another domain's internal files
import { validateBookingOverlap } from '@/domains/booking/internal/overlap-checker'
```

### Rule 2: Each Domain Owns Its Database Tables

```
identity domain     → users, driver_profiles, host_profiles, driver_vehicles
charging domain     → charger_listings, listing_availability_schedules, listing_blackout_dates
booking domain      → bookings
sessions domain     → charging_sessions, session_meter_values
payments domain     → transactions, payouts, payout_line_items, wallet_transactions
marketplace domain  → marketplace_products, installer_profiles, marketplace_jobs
ai_voice domain     → ai_conversations, voice_sessions, user_preferences
trust domain        → reviews, incidents, disputes, insurance_claims
compliance domain   → audit_log, gdpr_requests, kyc_verifications
region domain       → regions, tariff_rules, insurance_policies_by_region
```

### Rule 3: Domain Events for Cross-Domain Communication

When an event in one domain needs to trigger behaviour in another, use domain events — never direct function calls across domains.

```typescript
/**
 * @file domain-events.ts
 * @description Domain event definitions for cross-domain communication.
 * Published to an internal event bus (Redis pub/sub or EventEmitter).
 */

// Sessions domain publishes:
export type SessionCompletedEvent = {
  type: 'SESSION_COMPLETED'
  sessionId: string
  bookingId: string
  energyConsumedWh: number
  totalCostPence: number
  idleFeePence: number
}

// Payments domain subscribes → captures Stripe PaymentIntent
// Rewards domain subscribes → awards points for session
// Trust domain subscribes → updates listing stats
// Compliance domain subscribes → writes to audit log

// Booking domain publishes:
export type BookingConfirmedEvent = {
  type: 'BOOKING_CONFIRMED'
  bookingId: string
  driverId: string
  hostId: string
  listingId: string
  scheduledStart: Date
}

// AI/Voice domain subscribes → sends confirmation reminder
// Compliance domain subscribes → audit log entry
```

```typescript

// ❌ Never export: Internal helpers
```

## 7. Monolith → Microservices Migration Path

When the time comes to split, here is the procedure for each domain:

```
STEP 1: Verify domain boundary is clean
  → All cross-domain communication uses domain events
  → No direct imports from other domains
  → Domain has its own DB tables (no shared tables with other domains)

STEP 2: Extract domain to standalone service
  → Copy domain folder to new Railway service
  → Replace in-process event bus with Redis pub/sub
  → Add HTTP/gRPC API for sync calls
  → Update other domains to call the new service URL

STEP 3: Test in staging
  → Run full E2E test suite
  → Verify all domain event subscriptions still work
  → Verify API contracts unchanged

STEP 4: Deploy independently
  → Domain now has its own Railway deployment
  → Its own scaling rules
  → Its own monitoring alerts

STEP 5: Consider separate DB (if volume warrants)
  → Create new PostgreSQL instance for the extracted service
  → Migrate domain tables
  → Update connection strings
```

**Migration order (when the time comes):**
1. `ai-voice` — already a separate Python service ✅
2. `ocpp` — already a separate Node.js service ✅
3. `payments` — high transaction volume, independent scaling
4. `sessions` — high insert volume (meter_values), independent scaling
5. `marketplace` — independent commercial logic
6. `charging` — core domain, extract last

## 8. Event Bus Implementation

```typescript
/**
 * @file lib/events/event-bus.ts
 * @description Internal domain event bus.
 * Phase 1: In-process EventEmitter (fast, zero latency, no infra)
 * Phase 2: Redis pub/sub (when services split across processes)
 * Same API — switch underlying implementation, no domain code changes.
 */

interface EventBus {
  publish<T extends DomainEvent>(event: T): Promise<void>
  subscribe<T extends DomainEvent>(
    eventType: T['type'],
    handler: (event: T) => Promise<void>
  ): void
}

// Phase 1: In-process (monolith)
class InProcessEventBus implements EventBus {
  private emitter = new EventEmitter()

  async publish<T extends DomainEvent>(event: T) {
    this.emitter.emit(event.type, event)
  }

  subscribe<T extends DomainEvent>(type: T['type'], handler: (e: T) => Promise<void>) {
    this.emitter.on(type, handler)
  }
}

// Phase 2: Redis pub/sub (swap in when services split) — same interface
class RedisEventBus implements EventBus {
  async publish<T extends DomainEvent>(event: T) {
    await redis.publish(`domain-events:${event.type}`, JSON.stringify(event))
  }
  subscribe<T extends DomainEvent>(type: T['type'], handler: (e: T) => Promise<void>) {
    redis.subscribe(`domain-events:${type}`, async (msg) => handler(JSON.parse(msg)))
  }
}

// Export: switch phase by changing ONE line
export const eventBus: EventBus = new InProcessEventBus()
// Phase 2: export const eventBus: EventBus = new RedisEventBus()
```
