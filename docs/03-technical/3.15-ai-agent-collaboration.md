## 1. Agent Team Philosophy

A single monolithic AI agent handling everything becomes slow, unreliable, and hard to debug. Instead, Zipgrid uses a **team of specialised agents** that each own a domain — exactly mirroring the DDD bounded contexts in the codebase.

Each agent is an expert at one thing. When a task crosses domains, agents communicate and hand off — like a well-run team where the accountant handles money, the engineer handles hardware, and the concierge handles travel.

```
User request arrives
       │
       ▼
ORCHESTRATOR AGENT (Router)
  Understands intent → routes to the right specialist
       │
       ├──→ CHARGING AGENT     — session start/stop, charger status
       ├──→ BOOKING AGENT      — reservations, availability, cancellations
       ├──→ PLANNING AGENT     — trip planning, route, multi-stop charging
       ├──→ PRICING AGENT      — tariff optimisation, earnings suggestions
       ├──→ MAINTENANCE AGENT  — fault diagnosis, installer booking
       ├──→ SUPPORT AGENT      — customer issues, billing queries, disputes
       ├──→ FLEET AGENT        — fleet scheduling, ESG, policy enforcement
       └──→ KNOWLEDGE AGENT    — FAQ, how-to, product information (RAG)
```

## 2. Agent Definitions

### Orchestrator Agent (Router)

**Role:** Receives all user inputs (voice or text) and routes to the correct specialist agent. Never answers questions directly — it delegates.

**Input:** Raw user utterance + current context
**Output:** Routed request to specialist agent + context handoff
**Memory:** Short-term conversation history (last 10 turns)

```python
# ai_service/agents/orchestrator.py
"""
@file orchestrator.py
@description Routing agent — classifies intent and delegates to specialist.
Uses GPT-4o to classify intent from a user message and routes
to the appropriate specialist agent via the agent registry.
"""
ROUTING_SYSTEM_PROMPT = """
You are the Zipgrid routing agent. Your only job is to classify the user's
intent and route to the correct specialist. You do not answer questions yourself.

Available specialists: charging, booking, planning, pricing,
maintenance, support, fleet, knowledge.

Respond with: {"agent": "specialist_name", "confidence": 0.0-1.0}
"""
```

---

### Charging Agent

**Role:** Controls active charging sessions — start, stop, monitor, pause.
**Tools:** `start_session`, `stop_session`, `get_session_status`, `get_meter_values`
**Constraint:** Can only control sessions belonging to the requesting user.

**Example handoffs FROM Orchestrator:**
- "Start charging" → Charging Agent
- "Stop my session" → Charging Agent
- "How much have I charged?" → Charging Agent

**Example handoffs TO other agents:**
- Session completes → hands billing summary to Support Agent (if user questions bill)
- Fault detected during session → hands to Maintenance Agent

---

### Booking Agent

**Role:** Manages all reservation logic — create, confirm, cancel, modify.
**Tools:** `search_listings`, `check_availability`, `create_booking`, `cancel_booking`, `extend_booking`
**Constraint:** Cannot book on behalf of another user. All bookings tied to requesting user_id.

**Example:**
```
User: "Book a charger for tomorrow at 10am in Clapham"
Orchestrator → Booking Agent
Booking Agent:
  1. search_listings(lat=51.46, lng=-0.14, filters={available_at: "2027-01-07T10:00"})
  2. Returns top 3 results
  3. create_booking({listing_id: best_match, ...})
  4. Returns: "Booked — Sarah's driveway, tomorrow 10am. Code: ZG-8472"
```

---

### Planning Agent

**Role:** Multi-stop trip planning, route optimisation, corridor charging.
**Tools:** `calculate_route`, `find_corridor_chargers`, `batch_book_charging_stops`, `get_weather_range_penalty`
**External:** Mapbox Directions API, Open-Meteo weather API

**Agent-to-agent collaboration example:**
```
User: "Plan my trip to Manchester tomorrow"
Orchestrator → Planning Agent

Planning Agent:
  1. calculate_route(origin=user_location, dest="Manchester")
  2. get_weather_range_penalty(temp=forecast_temp, vehicle=user_vehicle)
  3. find_corridor_chargers(route_wkt, adjusted_range)
  → Returns trip plan with 2 stops

  4. Asks user: "I found 2 stops. Want me to book them?"
  5. If yes → hands to Booking Agent (agent-to-agent):
     booking_agent.batch_book([stop1_params, stop2_params])
  6. Returns: "Both stops booked. Have a good trip."
```

---

### Pricing Agent

**Role:** Tariff optimisation, earnings analytics, dynamic pricing suggestions.
**Tools:** `get_tariff_rates`, `schedule_smart_charging`, `suggest_listing_price`, `get_competitor_pricing`
**External:** Octopus Energy API, Open-Meteo (for demand forecasting)

**Proactive behaviour (Agentic mode only):**
- Monitors tariff rates hourly
- When cheap rate detected → automatically schedules charging (within user's boundary settings)
- When demand spike detected → notifies host with pricing suggestion

---

### Maintenance Agent

**Role:** Fault diagnosis, charger health monitoring, installer booking.
**Tools:** `diagnose_fault`, `search_installers`, `book_installer_job`, `get_charger_health_score`
**Knowledge:** Full OCPP fault code library in RAG

**Agent-to-agent collaboration example:**
```
OCPP StatusNotification: Faulted — GroundFailure
↓
Charging Agent detects fault → publishes domain event
↓
Maintenance Agent subscribes to fault events:
  1. diagnose_fault(error_code="GroundFailure", brand="EO Charging")
  → RAG returns: "Ground fault — wiring issue, requires licensed electrician"

  2. In Agentic mode:
     search_installers(location=charger_location, service="electrical_fault")
     → Returns nearest 3 OZEV+NICEIC certified engineers

  3. Notifies host:
     "Your charger has a wiring issue. I found Andy's EV Installs
      (4.9★) available tomorrow 10am for £85. Shall I book?"

  4. If yes: book_installer_job(installer_id, date, listing_id)
```

---

### Support Agent

**Role:** Customer support — billing queries, disputes, account issues.
**Tools:** `lookup_booking`, `lookup_session`, `lookup_transaction`, `issue_refund`, `create_dispute`, `escalate_to_human`
**Context:** Full user session data injected at every support conversation start

**Rule:** Support Agent is the only agent that can issue refunds — and only up to £50 without escalation. Over £50 → always escalates to human.

---

### Fleet Agent

**Role:** Fleet management, ESG reporting, driver policy enforcement.
**Tools:** `get_fleet_sessions`, `calculate_esg_metrics`, `enforce_spend_policy`, `generate_fleet_report`
**Access:** Only accessible to users with `fleet_manager` role.

---

### Knowledge Agent

**Role:** Answers questions from the knowledge base. Pure RAG — no tools, no actions.
**Tools:** None (read-only RAG queries)
**Knowledge:** Platform docs, charger manuals, tariff guides, UK EV regulations, FAQs

The Knowledge Agent is the fallback when no specialist can handle the query. If an intent is purely informational, it routes here directly.

## 3. Agent Communication Protocol

Agents communicate through a structured message format:

```python
# ai_service/core/agent_message.py
"""
@file agent_message.py
@description Inter-agent message format for agent-to-agent communication.
"""
from dataclasses import dataclass
from typing import Any, Optional

@dataclass
class AgentMessage:
    sender:       str           # e.g. "planning_agent"
    recipient:    str           # e.g. "booking_agent"
    task:         str           # e.g. "batch_book_charging_stops"
    params:       dict[str, Any]
    user_id:      str           # Always included — ownership validation
    session_id:   str           # Conversation session for traceability
    priority:     str           # 'normal' | 'urgent' (fault scenarios)
    context:      Optional[dict] = None  # Any data the recipient needs

@dataclass
class AgentResponse:
    sender:       str
    recipient:    str
    success:      bool
    result:       Any
    error:        Optional[str] = None
    next_agent:   Optional[str] = None  # Pass to another agent if needed
```

        sender="planning_agent",
        recipient="booking_agent",

        user_id=self.user_id,       # ALWAYS pass user_id

## 5. AI Agent Guard Rules (Enforced by All Agents)

Every agent, without exception, must enforce these rules:

```python
# ai_service/core/guards.py
"""
@file guards.py
@description Security guards enforced by all agents.
Import and apply these before any tool execution.
"""

def validate_ownership(tool_name: str, params: dict, user_id: str) -> None:
    """Raises PermissionError if params reference data not owned by user_id."""

def validate_tool_allowed(tool_name: str) -> None:
    """Raises PermissionError if tool_name not in ALLOWED_TOOL_NAMES."""

def validate_financial_limits(amount_pence: int, user_id: str) -> None:
    """Raises ValueError if amount exceeds user's AgenticBoundaries settings."""

def require_confirmation_for(action: str) -> bool:
    """Returns True if this action always requires user confirmation."""
    ALWAYS_CONFIRM = {'create_booking', 'cancel_booking', 'issue_refund',
                      'book_installer_job', 'make_payment', 'redeem_rewards'}
    return action in ALWAYS_CONFIRM
```

## 6. Agent Development Checklist

Before merging any new agent or agent modification:

```
□ Agent file has JSDoc header with: name, domain, tools, constraints
□ All tools imported from tools/ (no inline tool logic in agent)
□ validate_ownership() called before every tool execution
□ validate_tool_allowed() called on every tool name
□ Tests cover: normal operation, ownership violation, low-confidence rejection
□ Agent registered in AGENT_REGISTRY
□ Orchestrator routing prompt updated
□ Agent-to-agent handoffs use AgentMessage protocol
□ No agent writes directly to DB — all DB operations via domain services
□ No agent can call tools outside its defined scope
□ All financial actions go through validate_financial_limits()
```
