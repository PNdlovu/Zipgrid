# OCPP Integration Specification
## Zipgrid — Open Charge Point Protocol

| Field | Value |
|-------|-------|
| **Version** | 0.1 |
| **Protocols Supported** | OCPP 1.6J (launch) · OCPP 2.0.1 (Phase 2) |
| **Transport** | WebSocket (WSS) over TLS 1.3 |
| **Central System URL** | `wss://ocpp.zipgrid.co.uk/1.6/{chargePointId}` |
| **Last Updated** | September 24, 2026 |

---

## 1. Overview

The Zipgrid OCPP Central System is a standalone Node.js WebSocket service that maintains persistent connections with every paired smart charger. It is the real-time bridge between physical charging hardware and the Zipgrid platform — receiving telemetry, issuing remote commands, and publishing events to the main application.

```
EV ←→ Smart Charger ←─ OCPP 1.6J WebSocket ─→ Zipgrid Central System
                                                        │
                                              ┌─────────┴──────────┐
                                              │                    │
                                         PostgreSQL           Redis pub/sub
                                         (persist events)     (real-time push
                                                               to driver app)
```

### Why standalone service
WebSocket connections are long-lived — a single 8-hour charging session maintains one persistent connection. Vercel Serverless Functions timeout after 30 seconds and cannot hold long-lived connections. The OCPP service runs as a persistent Node.js process on Railway with auto-restart on failure.

## 2. Protocol Overview — OCPP 1.6J

OCPP 1.6 JSON (1.6J) uses WebSocket framing with JSON message arrays.

### Message Types

```
[2, uniqueId, action, payload]    ← CALL (sender initiates)
[3, uniqueId, payload]            ← CALLRESULT (receiver responds)
[4, uniqueId, errorCode, errorDescription, errorDetails] ← CALLERROR
```

### Connection Lifecycle

```
Charger powers on
      │
      ▼
WebSocket connect to wss://ocpp.zipgrid.co.uk/1.6/{chargePointId}
      │
      ▼ CALL
BootNotification { chargePointVendor, chargePointModel, firmwareVersion }
      │
      ▼ CALLRESULT
BootNotification.conf { status: "Accepted", currentTime, heartbeatInterval }
      │
      ▼ (every heartbeatInterval seconds)
Heartbeat {}  →  Heartbeat.conf { currentTime }
      │
      ▼ (when connector state changes)
StatusNotification { connectorId, status, errorCode }
      │
      ▼ (when driver plugs in and platform authorises)
Authorize { idTag }  →  Authorize.conf { idTagInfo: { status: "Accepted" } }
      │
      ▼
StartTransaction { connectorId, idTag, meterStart, timestamp }
      │
      ▼ CALLRESULT
StartTransaction.conf { transactionId, idTagInfo }
      │
      ▼ (every 60–300 seconds)
MeterValues { connectorId, transactionId, meterValue: [...] }
      │
      ▼ (on vehicle disconnect, remote stop, or driver taps Stop)
StopTransaction { transactionId, meterStop, timestamp, reason }
      │
      ▼ CALLRESULT
StopTransaction.conf { idTagInfo }
```

## 3. Message Reference — Charger → Central System (Initiated by Charger)

### 3.1 BootNotification

Sent by charger on power-on or reconnect. Central System MUST respond within 30 seconds.

**CALL**
```json
[2, "19223201", "BootNotification", {
  "chargePointVendor": "EO Charging",
  "chargePointModel": "EO Mini Pro 3",
  "chargePointSerialNumber": "EO-2023-00042",
  "firmwareVersion": "3.2.1",
  "iccid": "",
  "imsi": ""
}]
```

**CALLRESULT**
```json
[3, "19223201", {
  "currentTime": "2027-01-06T09:00:00.000Z",
  "interval": 300,
  "status": "Accepted"
}]
```

**Central System actions:**
- Update `charger_listings.ocpp_last_seen` timestamp
- If charger was `offline`, update status to `online`
- Log `BootNotification` to `ocpp_event_log`

---

### 3.2 Heartbeat

Sent at the interval specified in `BootNotification.conf`. Confirms charger is still online.

**CALL**
```json
[2, "19223202", "Heartbeat", {}]
```

**CALLRESULT**
```json
[3, "19223202", {
  "currentTime": "2027-01-06T09:05:00.000Z"
}]
```

**Central System actions:**
- Update `last_heartbeat_at` in connection store (Redis)
- If no heartbeat for > 2× heartbeat interval → mark charger `offline`, alert host

---

### 3.3 StatusNotification

Sent when connector or charger status changes.

**CALL**
```json
[2, "19223203", "StatusNotification", {
  "connectorId": 1,
  "errorCode": "NoError",
  "status": "Charging",
  "timestamp": "2027-01-06T09:01:15.000Z",
  "info": "",
  "vendorId": "",
  "vendorErrorCode": ""
}]
```

**Status values and Zipgrid mapping:**

| OCPP Status | Zipgrid Display | Action |
|------------|-----------------|--------|
| `Available` | Available | Update listing status; allow bookings |
| `Preparing` | Preparing | Driver plugged in; awaiting StartTransaction |
| `Charging` | Charging ⚡ | Update session status; push to driver app |
| `SuspendedEV` | Paused (EV) | EV battery management pause — normal |
| `SuspendedEVSE` | Paused (Charger) | Charger-initiated pause — investigate if prolonged |
| `Finishing` | Finishing | Transaction ending — capture final meter |
| `Reserved` | Reserved | Booking confirmed, slot locked |
| `Unavailable` | Unavailable | Charger taken offline by host |
| `Faulted` | Fault ⚠️ | Alert host; trigger agentic fault workflow |

**Error codes triggering agentic fault workflow:**
```
ConnectorLockFailure  GroundFailure  HighTemperature  InternalError
LocalListConflict     NoError        OtherError       OverCurrentFailure
OverVoltage           PowerMeterFailure  PowerSwitchFailure  ReaderFailure
ResetFailure          UnderVoltage  WeakSignal
```

---

### 3.4 Authorize

Charger requests authorisation for an RFID tag or platform-generated idTag before starting a transaction. Zipgrid uses platform-generated idTags (UUID-based) rather than physical RFID cards.

**CALL**
```json
[2, "19223204", "Authorize", {
  "idTag": "ZG-8472-SESS-UUID"
}]
```

**CALLRESULT — Accepted**
```json
[3, "19223204", {
  "idTagInfo": {
    "status": "Accepted",
    "expiryDate": "2027-01-06T11:00:00.000Z"
  }
}]
```

**CALLRESULT — Rejected** (booking not found, expired, wrong charger)
```json
[3, "19223204", {
  "idTagInfo": { "status": "Invalid" }
}]
```

---

### 3.5 StartTransaction

Sent when charging actually begins (after Authorize accepted and cable connected).

**CALL**
```json
[2, "19223205", "StartTransaction", {
  "connectorId": 1,
  "idTag": "ZG-8472-SESS-UUID",
  "meterStart": 45820000,
  "timestamp": "2027-01-06T09:01:15.000Z",
  "reservationId": null
}]
```

**Note:** `meterStart` is in **Wh** (Watt-hours). Store raw Wh; convert to kWh only for display.

**CALLRESULT**
```json
[3, "19223205", {
  "transactionId": 10042,
  "idTagInfo": { "status": "Accepted" }
}]
```

**Central System actions:**
- Create `charging_sessions` row with `ocpp_transaction_id: 10042`, `meter_start_wh: 45820000`
- Update `bookings.status` → `confirmed` (if instant book) / stays `confirmed`
- Publish session start event to Redis → push notification to driver
- Begin expecting MeterValues

---

### 3.6 MeterValues

Sent periodically during charging. Contains energy, power, current, voltage, and optionally SoC.

**CALL**
```json
[2, "19223206", "MeterValues", {
  "connectorId": 1,
  "transactionId": 10042,
  "meterValue": [
    {
      "timestamp": "2027-01-06T09:31:00.000Z",
      "sampledValue": [
        {
          "value": "45925700",
          "context": "Sample.Periodic",
          "format": "Raw",
          "measurand": "Energy.Active.Import.Register",
          "unit": "Wh"
        },
        {
          "value": "11300",
          "measurand": "Power.Active.Import",
          "unit": "W"
        },
        {
          "value": "47.1",
          "measurand": "Current.Import",
          "unit": "A"
        },
        {
          "value": "240.1",
          "measurand": "Voltage",
          "unit": "V"
        },
        {
          "value": "58",
          "measurand": "SoC",
          "unit": "Percent"
        }
      ]
    }
  ]
}]
```

**CALLRESULT**
```json
[3, "19223206", {}]
```

**Central System actions:**
- Insert row into `session_meter_values` (BIGSERIAL — high throughput)
- Calculate `energy_consumed_wh` = latest reading − `meter_start_wh`
- Publish to Redis channel `session:{sessionId}:meters`
- Supabase Realtime broadcasts to driver app WebSocket (< 5s latency)
- Check for idle: if power < 0.1 kW for > 5 min → set `idle_started_at`, begin idle fee timer
- Check for thermal: if temperature > 65°C → alert host

**MeterValues interval configuration:**
Zipgrid sets `MeterValueSampleInterval` via ChangeConfiguration message during device pairing:
```json
{ "key": "MeterValueSampleInterval", "value": "60" }
```
60 seconds is the default. Configurable per charger brand (some default to 300s).

---

### 3.7 StopTransaction

Sent when charging ends (vehicle disconnects, driver taps Stop, or session timeout).

**CALL**
```json
[2, "19223207", "StopTransaction", {
  "transactionId": 10042,
  "idTag": "ZG-8472-SESS-UUID",
  "meterStop": 46043200,
  "timestamp": "2027-01-06T11:07:48.000Z",
  "reason": "EVDisconnected",
  "transactionData": []
}]
```

**Stop reason values:**

| Reason | Meaning |
|--------|---------|
| `EVDisconnected` | Cable unplugged by driver — normal end |
| `Local` | Stop button pressed on charger hardware |
| `Remote` | Zipgrid RemoteStopTransaction — driver tapped "Stop" in app |
| `HardReset` | Charger rebooted during session |
| `EmergencyStop` | Emergency stop button activated |
| `PowerLoss` | Power cut |
| `Reboot` | Planned charger restart |
| `Other` | Any other reason |

**CALLRESULT**
```json
[3, "19223207", {
  "idTagInfo": { "status": "Accepted" }
}]
```

**Central System actions:**
- Update `charging_sessions`: `meter_stop_wh`, `ended_at`, `status: completed`, `stop_reason`
- Calculate `energy_consumed_wh` = `meter_stop_wh` − `meter_start_wh`
- Calculate final idle fee if applicable
- Trigger Stripe PaymentIntent capture via Next.js API webhook
- Update `bookings.status` → `completed`
- Fire `update_listing_stats_on_session_complete` trigger
- Push session completion notification to driver
- Prompt driver review

## 4. Message Reference — Central System → Charger (Platform-Initiated)

### 4.1 RemoteStartTransaction

Platform initiates a charge session (driver taps "Start Session" in app, or agentic scheduler triggers).

**CALL (Central System → Charger)**
```json
[2, "19223208", "RemoteStartTransaction", {
  "connectorId": 1,
  "idTag": "ZG-8472-SESS-UUID",
  "chargingProfile": null
}]
```

**CALLRESULT (Charger → Central System)**
```json
[3, "19223208", { "status": "Accepted" }]
```

Status options: `Accepted` · `Rejected` (charger busy or offline)

**Zipgrid flow:**
```
Driver taps "Start Charging" in app
  → POST /api/v1/sessions/start
  → Central System looks up active WebSocket for chargePointId
  → Sends RemoteStartTransaction with booking's idTag
  → Charger responds Accepted
  → API returns 201 to driver app
  → Charger sends StatusNotification (Preparing → Charging)
  → Charger sends StartTransaction (confirms session is live)
```

---

### 4.2 RemoteStopTransaction

Platform stops an active session (driver taps "Stop Charging" in app, or idle fee threshold reached).

**CALL (Central System → Charger)**
```json
[2, "19223209", "RemoteStopTransaction", {
  "transactionId": 10042
}]
```

**CALLRESULT**
```json
[3, "19223209", { "status": "Accepted" }]
```

---

### 4.3 ChangeAvailability

Platform sets a connector to Unavailable (e.g. host pauses listing, maintenance mode).

**CALL**
```json
[2, "19223210", "ChangeAvailability", {
  "connectorId": 0,
  "type": "Inoperative"
}]
```

Restore: `type: "Operative"`

---

### 4.4 ChangeConfiguration

Platform pushes configuration to charger during pairing or maintenance.

**CALL**
```json
[2, "19223211", "ChangeConfiguration", {
  "key": "MeterValueSampleInterval",
  "value": "60"
}]
```

**Key configurations set during pairing:**

| Key | Value | Purpose |
|-----|-------|---------|
| `MeterValueSampleInterval` | `60` | Send meter readings every 60 seconds |
| `HeartbeatInterval` | `300` | Heartbeat every 5 minutes |
| `ConnectionTimeOut` | `60` | Abort if no StartTransaction within 60s of Authorize |
| `StopTransactionOnEVSideDisconnect` | `true` | Auto-stop when cable unplugged |
| `AuthorizeRemoteTxRequests` | `true` | Require Authorize before RemoteStart |
| `LocalPreAuthorize` | `false` | Force all authorisation through Central System |
| `WebSocketPingInterval` | `60` | WS keepalive ping frequency |

---

### 4.5 GetConfiguration

Platform reads current charger configuration.

**CALL**
```json
[2, "19223212", "GetConfiguration", {
  "key": ["MeterValueSampleInterval", "HeartbeatInterval"]
}]
```

---

### 4.6 Reset

Platform reboots the charger (hard or soft).

**CALL**
```json
[2, "19223213", "Reset", { "type": "Soft" }]
```

`Soft` = graceful restart (completes active transaction first). `Hard` = immediate reboot.

---

### 4.7 TriggerMessage

Platform requests the charger to send a specific message immediately (diagnostic tool).

**CALL**
```json
[2, "19223214", "TriggerMessage", {
  "requestedMessage": "StatusNotification",
  "connectorId": 1
}]
```

Useful for: `StatusNotification` · `MeterValues` · `BootNotification` · `Heartbeat`

## 5. Smart Charging — OCPP 1.6 Charging Profiles

Zipgrid uses Charging Profiles to implement smart tariff scheduling (off-peak charging).

### 5.1 SetChargingProfile

Schedule a charging session for 2am–6am (Octopus Go cheap rate):

**CALL**
```json
[2, "19223215", "SetChargingProfile", {
  "connectorId": 1,
  "csChargingProfiles": {
    "chargingProfileId": 1,
    "stackLevel": 0,
    "chargingProfilePurpose": "TxDefaultProfile",
    "chargingProfileKind": "Recurring",
    "recurrencyKind": "Daily",
    "chargingSchedule": {
      "duration": 14400,
      "startSchedule": "2027-01-07T02:00:00Z",
      "chargingRateUnit": "A",
      "chargingSchedulePeriod": [
        { "startPeriod": 0,     "limit": 48 },
        { "startPeriod": 14400, "limit": 0  }
      ]
    }
  }
}]
```

**Agentic scheduling flow:**
```
Octopus Agile API returns tomorrow's half-hourly rates
  → AI agent identifies cheapest 4-hour window (e.g. 01:30–05:30)
  → Agent calls SetChargingProfile with that window
  → Charger begins charging at 01:30 automatically
  → Charger stops at 05:30 automatically
  → Driver wakes up to full battery at cheap rate
```

## 7. Connection Management

### 7.1 Connection Store (Redis)

Active WebSocket connections stored in Redis with TTL:

```
KEY: ocpp:connection:{chargePointId}
VALUE: {
  "serviceInstanceId": "railway-ocpp-01",
  "connectedAt": "2027-01-06T08:00:00Z",
  "lastHeartbeatAt": "2027-01-06T09:04:58Z",
  "status": "online",
  "activeTransactionId": 10042,
  "firmwareVersion": "3.2.1"
}
TTL: 600 seconds (refreshed on every heartbeat)
```

If TTL expires without a heartbeat → charger is considered offline.

### 7.2 Multi-Instance Routing

When the OCPP service scales to multiple Railway instances, each connection is pinned to one instance. Redis stores the `serviceInstanceId` so that RemoteStart/Stop commands are routed to the correct instance holding that WebSocket.

```
Next.js API → POST /ocpp/remote-start { chargePointId, ... }
  → OCPP Service checks Redis: which instance holds chargePointId?
  → Routes command to correct instance via Redis pub/sub
  → That instance sends RemoteStartTransaction over its WS connection
```

### 7.3 Reconnection Handling

Chargers reconnect automatically after network interruption. On reconnect:
1. Charger sends `BootNotification`
2. Central System checks for incomplete transactions in DB (in-progress session with no `StopTransaction`)
3. If found: Central System sends `RemoteStopTransaction` to terminate cleanly, or waits for charger to resume MeterValues (if transaction still active on charger side)
4. If transaction cannot be recovered: session marked `timed_out`, partial charge captured, driver notified

## 8. OCPP 2.0.1 — Phase 2 Roadmap

OCPP 2.0.1 adds:

| Feature | Benefit for Zipgrid |
|---------|---------------------|
| **TLS + certificate-based auth** | Replaces Basic Auth; OCPP charger identity is cryptographically verified |
| **ISO 15118 (Plug & Charge)** | EV authenticates itself — no app needed to start session |
| **Smart Charging Profiles (enhanced)** | More granular power scheduling; works with V2G |
| **Device Management** | Remote firmware updates, diagnostics |
| **Transaction events** | Replaces StartTransaction/StopTransaction with richer event model |
| **Cost information** | Platform can push live pricing to charger display screen |

OCPP 2.0.1 implementation is scoped for Phase 2 (Month 12+). The Central System will support both 1.6J and 2.0.1 simultaneously via version negotiation on WebSocket handshake.

## 9. Security

### OCPP 1.6J
- Transport: WSS (TLS 1.3)
- Authentication: HTTP Basic Auth in WebSocket URL
  `wss://charger-id:api-key@ocpp.zipgrid.co.uk/1.6/{chargePointId}`
- API key generated per charger at pairing; stored hashed in DB
- Rate limiting: max 10 CALL messages/second per chargePointId (prevent DoS)

### OCPP 2.0.1 (Phase 2)
- Transport: WSS (TLS 1.3)
- Authentication: TLS mutual authentication (client certificates)
- Per-charger certificate issued and revocable via platform

### idTag Security
- idTags are UUID-v4 + session binding: `ZG-{bookingShortCode}-{sessionUUID}`
- Single-use: idTag is invalidated after `StartTransaction` is received
- Time-limited: idTag expires at `scheduledEnd` + 30 minutes buffer
- If wrong idTag presented to charger → `Authorize.conf { status: "Invalid" }` → session blocked

## 10. Fault Handling & Alerting

### Fault Detection Flow

```
Charger sends StatusNotification { status: "Faulted", errorCode: "GroundFailure" }
  │
  ▼
Central System:
  1. Updates charger status in Redis and DB to "faulted"
  2. If active session: send RemoteStopTransaction
  3. Publish fault event to Redis
  │
  ▼
Next.js API receives fault webhook:
  1. Notify host (push + email): "Your charger has a fault — GroundFailure"
  2. Pause listing (no new bookings accepted)
  3. If active booking affected: cancel with full refund
  │
  ▼
AI Agent (POST /ai/diagnose):
  1. Looks up errorCode in OCPP fault code knowledge base
  2. Generates diagnosis + recommended action
  3. If action = "needs engineer": searches marketplace for nearest available installer
  4. Presents booking options to host (with confirmation gate)
```

### Alerting Thresholds

| Condition | Alert | Action |
|-----------|-------|--------|
| No heartbeat for 2× interval | Ops + host alert | Mark offline; investigate |
| StatusNotification: Faulted | Host alert + AI diagnosis | Pause listing |
| MeterValues stop during active session | Ops alert | Check WS connection; probe with TriggerMessage |
| Temperature > 65°C | Ops + host alert | Consider emergency RemoteStop |
| Session > 8hrs with no StopTransaction | Ops alert | Investigate stuck session |
| Authorize rejected 3× for same idTag | Security alert | Possible idTag brute force |
| > 50 messages/second from one charger | Security alert | Rate limit + investigate |
