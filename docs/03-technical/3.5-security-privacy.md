## 1. Security Principles

1. **Defence in depth** — multiple independent layers; no single point of failure
2. **Least privilege** — users, services, and DB roles can only access what they need
3. **Zero trust** — every request is authenticated and authorised, regardless of source
4. **Data minimisation** — collect only what is necessary; delete on schedule
5. **Secure by default** — new features are locked down first; access granted explicitly
6. **Auditability** — every sensitive action is logged immutably

## 3. Authentication & Session Security

### JWT Configuration

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Algorithm | HS256 (access) / RS256 (refresh) | HS256 for speed; RS256 for refresh token non-repudiation |
| Access token TTL | 15 minutes | Short window limits blast radius of leaked token |
| Refresh token TTL | 7 days | Reasonable UX; rotated on every use |
| Refresh token storage | HttpOnly cookie (web) / Secure keychain (mobile) | Prevents XSS access to refresh token |
| Access token storage | Memory only (web); no localStorage | localStorage is XSS-accessible |
| Token claims | `sub` (userId), `roles`, `kycStatus`, `iat`, `exp` | Role in token avoids DB lookup on every request |
| Refresh rotation | Single-use; old token immediately invalidated | Detects refresh token theft |

### Login Security

- **Rate limiting:** 5 failed login attempts → 15-minute lockout (Upstash Redis counter)
- **Credential stuffing protection:** Cloudflare Turnstile on login form (CAPTCHA-less bot detection)
- **Account enumeration prevention:** Password reset always returns 200 regardless of email existence
- **Timing-safe comparison:** Password comparison uses `bcrypt.compare` (constant-time)
- **Bcrypt cost factor:** 12 (balances security vs. login latency)

### Multi-Factor Authentication (Phase 2)

- TOTP (Authenticator app) via `otpauth` library
- Required for: admin accounts (at launch), host accounts with earnings > £500/month (Phase 2)
- Backup codes: 8× single-use codes, bcrypt-hashed in DB

## 4. Authorisation

### Row-Level Security (RLS) — Supabase/PostgreSQL

Critical tables have RLS policies enforced at the database layer — even if application code has a bug, the DB prevents unauthorised data access.

```sql
-- Example: drivers can only read their own bookings
CREATE POLICY "drivers_read_own_bookings"
ON bookings FOR SELECT
USING (
  driver_profile_id IN (
    SELECT id FROM driver_profiles WHERE user_id = auth.uid()
  )
);

-- Example: hosts can read bookings on their listings
CREATE POLICY "hosts_read_own_listing_bookings"
ON bookings FOR SELECT
USING (
  listing_id IN (
    SELECT id FROM charger_listings
    WHERE host_profile_id IN (
      SELECT id FROM host_profiles WHERE user_id = auth.uid()
    )
  )
);
```

### Database Role Separation

| Role | Access | Used by |
|------|--------|---------|
| `app_role` | SELECT/INSERT/UPDATE on user-facing tables | Next.js API |
| `ocpp_role` | SELECT on listings, INSERT/UPDATE on sessions + meter_values | OCPP Service |
| `ai_role` | SELECT on listings, sessions, preferences (read-only) | AI Service |
| `admin_role` | Full access except UPDATE/DELETE on audit_log | Admin panel |
| `readonly_role` | SELECT only | Analytics queries, BI tools |

`REVOKE UPDATE, DELETE ON audit_log FROM ALL;` — audit log is append-only at DB level.

### API Route Guards

```typescript
// middleware.ts — applied to all /api/v1/* routes
export function middleware(request: NextRequest) {
  const token = extractBearerToken(request);

  if (!token) return unauthorizedResponse();

  const payload = verifyJWT(token);
  if (!payload) return unauthorizedResponse();

  // Role check for admin routes
  if (request.nextUrl.pathname.startsWith('/api/v1/admin')) {
    if (!payload.roles.includes('admin')) return forbiddenResponse();
  }

  // KYC check for host routes (listings, payouts)
  if (isHostRoute(request.nextUrl.pathname)) {
    if (payload.kycStatus !== 'verified') {
      return errorResponse('KYC_REQUIRED', 403);
    }
  }
}
```

## 5. Data Encryption

### In Transit
- TLS 1.3 on all connections (HTTPS, WSS for OCPP, API calls to third parties)
- HSTS header: `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
- Certificate: Let's Encrypt (auto-renewed) via Vercel and Railway

### At Rest
- **Database:** Supabase encrypts all data at rest (AES-256) at the storage layer
- **Access codes / gate codes:** Application-level encryption before storing in `access_instructions`
  - Algorithm: AES-256-GCM
  - Key: stored in Vercel Environment Variable (not in DB)
  - Decrypted only at booking confirmation time for the specific driver

### Field-Level Encryption

| Field | Encrypted? | Method |
|-------|-----------|--------|
| `access_instructions` | ✅ Yes | AES-256-GCM (app layer) |
| `password_hash` | ✅ Yes | bcrypt (one-way hash) |
| KYC documents | ✅ Yes | Stripe Identity (never touches Zipgrid servers) |
| Payment card data | ✅ N/A | Never stored — Stripe handles entirely |
| `stripe_customer_id` | Plain (not sensitive) | Reference only |
| Email addresses | Plain | Needed for search |
| Phone numbers | Plain | Needed for SMS |

## 6. Payment Security — PCI-DSS

Zipgrid is **PCI-DSS SAQ A** compliant — the simplest tier, because:
- No card data ever passes through Zipgrid servers
- All card collection is via Stripe Elements (hosted iframes) or Stripe SDKs
- Stripe is a PCI-DSS Level 1 Service Provider

**Requirements:**
- Stripe.js loaded only from `js.stripe.com` (SRI hash validated)
- Content Security Policy prevents loading Stripe from any other source
- No cardholder data stored in Zipgrid DB (only Stripe's `pm_*` and `cus_*` IDs)
- Webhook signatures validated with `stripe.webhooks.constructEvent()` before processing

## 7. UK GDPR Compliance

### Legal Basis for Processing

| Data Category | Legal Basis | Retention |
|--------------|-------------|-----------|
| Account registration data (name, email) | Contract performance | Duration of account + 2 years |
| Payment transaction records | Legal obligation (financial records) | 7 years (HMRC requirement) |
| Session telemetry (kWh, timestamps) | Contract performance | 24 months then anonymised |
| KYC documents | Legal obligation (AML) | 5 years after account closure |
| Location data (charger locations) | Legitimate interest | Duration of listing + 1 year |
| Voice recordings | Consent (explicit, at voice feature setup) | 30 days then deleted |
| AI conversation history | Consent | 30 days or until user deletes |
| Marketing communications | Consent | Until unsubscribe |
| Audit logs | Legitimate interest (security, fraud prevention) | 7 years |

### Data Subject Rights

| Right | Implementation | Response Time |
|-------|---------------|---------------|
| **Right of access (SAR)** | In-app "Download my data" button → async export job → email download link | 72 hours (max 30 days by law) |
| **Right to erasure** | In-app "Delete my account" → anonymises PII fields; retains legally required records | 30 days (max) |
| **Right to portability** | JSON export of all personal data | 72 hours |
| **Right to rectification** | Self-service profile editing for most fields; support form for others | 72 hours |
| **Right to object** | Unsubscribe from marketing; disable AI conversation logging | Immediate |
| **Right to restrict processing** | Support team manual process | 30 days |

### Data Protection by Design

- **Data minimisation:** Collect only fields essential to platform function
- **Purpose limitation:** Data used only for the purpose stated at collection
- **Storage limitation:** Automated retention jobs run monthly; data past retention window anonymised
- **Accuracy:** Users can update profile data at any time
- **Privacy notices:** Plain English, not legal boilerplate

### ICO Registration
Zipgrid must register with the Information Commissioner's Office (ICO) as a data controller before handling any personal data. Annual fee: £40–£60 (Tier 1).

### Data Breach Protocol

```
Breach detected (security alert, user report, or internal discovery)
  │
  ▼
Incident lead assesses within 1 hour:
  - What data was exposed?
  - How many users affected?
  - Is ongoing exposure possible?
  │
  ▼ If >250 users affected OR high-risk data (passwords, payment refs, KYC)
  │
  ▼
Report to ICO within 72 hours (UK GDPR requirement)
  + Notify affected users within 72 hours (if likely high risk to rights/freedoms)
  │
  ▼

Remediation actions with owners and deadlines
```

## 8. OCPP Security

### Charger Authentication
- Each charger has a unique `chargePointId` and `apiKey` generated at pairing
- Credentials are provided to host during OCPP setup in-app
- `apiKey` stored as bcrypt hash in `charger_listings` table
- OCPP WebSocket URL: `wss://{chargePointId}:{apiKey}@ocpp.zipgrid.co.uk/1.6/{chargePointId}`

### idTag Security
- Platform-generated idTags are UUID v4 bound to a specific booking+session
- Single-use: invalidated after `StartTransaction` confirmation
- Time-limited: expires at `scheduledEnd` + 30 minutes
- If unauthorized idTag → `Authorize.conf: Invalid` → no session starts

### Command Injection Prevention
- All OCPP messages validated against OCPP 1.6 JSON schema before processing
- `chargePointId` extracted from WebSocket URL, never from message payload
- `transactionId` in `RemoteStopTransaction` cross-referenced against active sessions in DB — platform cannot be tricked into stopping a session it didn't start
- Message rate limiting: 10 messages/second per charger

## 9. AI & Voice Security

### Prompt Injection Prevention
The AI service is vulnerable to prompt injection — malicious user input designed to override system instructions.

**Mitigations:**
- System prompt is immutable and loaded from environment config (not user input)
- User input is sandboxed in a separate `human_message` field — never concatenated into system prompt
- Tool calls only execute against allowlisted functions (no arbitrary code execution)
- LangChain tool inputs are validated against Zod schemas before execution
- Maximum input length: 1,000 characters for voice commands; 500 for Q&A

### Voice Data
- Voice audio processed in-browser via Web Speech API where possible (audio never leaves device)
- When Whisper API is used: audio sent directly to OpenAI API (Zipgrid never stores audio)
- Voice session transcripts stored for 30 days for QA purposes (user can opt out)
- Voice data never used to train models without explicit user consent

### RAG Knowledge Base Integrity
- Knowledge base documents managed by platform team only (no public contribution to indexed corpus)
- Community-contributed guides go through moderation before indexing
- Vector embeddings regenerated if source documents are updated or removed

## 10. Infrastructure Security

### Secret Management
- All secrets stored in Vercel Environment Variables (Next.js) and Railway Variables (services)
- Never committed to source code or `.env` files
- Secret rotation schedule: Stripe keys quarterly; JWT keys every 6 months; OCPP API keys on request

### Security Headers (Next.js)
```typescript
// next.config.ts
headers: [
  { key: 'X-Frame-Options',           value: 'DENY' },
  { key: 'X-Content-Type-Options',     value: 'nosniff' },
  { key: 'Referrer-Policy',            value: 'strict-origin-when-cross-origin' },
  { key: 'Permissions-Policy',         value: 'camera=(), microphone=(self), geolocation=(self)' },
  { key: 'Strict-Transport-Security',  value: 'max-age=63072000; includeSubDomains; preload' },
  {
    key: 'Content-Security-Policy',
    value: [
      "default-src 'self'",
      "script-src 'self' https://js.stripe.com https://maps.googleapis.com",
      "frame-src https://js.stripe.com",
      "connect-src 'self' https://api.stripe.com wss://ocpp.zipgrid.co.uk",
      "img-src 'self' data: https://cdn.zipgrid.co.uk",
    ].join('; ')
  }
]
```

### Dependency Security
- `npm audit` runs in every CI pipeline — fails build on critical vulnerabilities
- Dependabot enabled on GitHub — automated PRs for dependency updates
- Weekly manual review of high/critical audit findings
- `package-lock.json` pinned and committed

### Penetration Testing
- External pen test commissioned before public launch (CREST-accredited firm)
- Annual pen test thereafter
- Bug bounty programme (Responsible Disclosure Policy published at `zipgrid.co.uk/security`)

## 11. SOC 2 Type I Roadmap

Target: SOC 2 Type I certificate within 12 months of launch.

**Trust Service Criteria covered:**
- **Security** (mandatory)
- **Availability** (for session uptime SLA commitments to hosts)
- **Confidentiality** (for KYC data and access codes)
- **Processing Integrity** (for financial transaction accuracy)

**Compliance automation:** Vanta (continuous monitoring, evidence collection, auditor portal)

**Timeline:**
```
Month 1:   Vanta onboarded; initial gap assessment
Month 2–6: Implement control gaps (access reviews, vendor assessments, training)
Month 7:   Readiness assessment with auditor (Prescient Assurance or similar)
Month 8–10: Observation period
Month 11: Type I audit
Month 12: SOC 2 Type I report issued
```
