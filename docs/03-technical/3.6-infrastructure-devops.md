## 3. Vercel — Next.js Application

### Configuration

```json
// vercel.json
{
  "regions": ["lhr1"],
  "functions": {
    "app/api/**": { "maxDuration": 30 }
  },
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "X-Content-Type-Options", "value": "nosniff" }
      ]
    }
  ]
}
```

- **Primary region:** `lhr1` (London Heathrow) — lowest latency for UK users
- **Edge functions:** Auth middleware, geo-IP detection, A/B test assignment
- **Serverless functions:** All API routes (`/api/v1/*`)
- **ISR (Incremental Static Regeneration):** Listing detail pages revalidate every 60 seconds
- **React Server Components:** Map search results, marketplace listing pages (SEO)
- **Vercel Blob:** Photo uploads (listing photos, avatar uploads) — served via CDN

### Caching Strategy

| Route Type | Strategy | Revalidation |
|------------|----------|-------------|
| Listing detail page | ISR | 60 seconds |
| Map search results | No cache (dynamic geo query) | — |
| Marketplace products | ISR | 300 seconds |
| Knowledge base articles | ISR | 3600 seconds |
| Active session screen | No cache | — |
| Static pages (home, about) | Static | Deploy-time |

## 4. Railway — OCPP & AI Services

### OCPP Service (Node.js)

```yaml
# railway.toml (OCPP service)
[build]
  builder = "NIXPACKS"
  buildCommand = "npm ci"

[deploy]
  startCommand = "node dist/server.js"
  restartPolicyType = "ON_FAILURE"
  restartPolicyMaxRetries = 10
  healthcheckPath = "/health"
  healthcheckTimeout = 30

[[services]]
  name = "ocpp-service"
  numReplicas = 2          # Two instances for HA
  resources:
    cpu = "1 vCPU"
    memory = "512 MB"
```

**Health check endpoint:**
```
GET /health
→ { "status": "ok", "connections": 142, "uptime": 86400 }
```

**Scaling triggers:**
- CPU > 70% for 5 minutes → scale to 3 instances
- WebSocket connection count > 5,000 per instance → scale out
- Manual scale via Railway dashboard or CLI

### AI/Voice Service (Python FastAPI)

```yaml
# railway.toml (AI service)
[build]
  builder = "NIXPACKS"
  buildCommand = "pip install -r requirements.txt"

[deploy]
  startCommand = "uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4"
  healthcheckPath = "/health"
  resources:
    cpu = "2 vCPU"
    memory = "2 GB"        # LangChain + embedding models need headroom
```

**Worker model:** 4 Uvicorn workers per instance. LLM calls are I/O-bound (network to OpenAI API) so multiple workers handle concurrent requests efficiently.

### Service-to-Service Authentication

Internal services communicate over Railway's private network using HMAC-signed requests:

```typescript
// Shared auth utility
function signServiceRequest(payload: object, secret: string): string {
  const body = JSON.stringify(payload);
  const signature = createHmac('sha256', secret).update(body).digest('hex');
  return `sha256=${signature}`;
}

// Next.js → OCPP Service
fetch('http://ocpp-service.railway.internal/remote-start', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-Service-Signature': signServiceRequest(payload, OCPP_SERVICE_SECRET),
  },
  body: JSON.stringify(payload),
});
```

## 5. Supabase — Database

### Connection Strategy

```
Next.js API routes      → Supabase connection pooler (pgBouncer)
                          Port 6543 — transaction mode
                          Max pool size: 20 per Supabase instance

DB migrations           → Supabase direct connection
                          Port 5432 — session mode

OCPP Service            → Direct connection (persistent session)
                          Small pool: 5 connections max

Supabase Realtime       → Managed by Supabase SDK
                          WebSocket subscription per active session
```

### Database Maintenance

```sql
-- pg_cron jobs (set up in Supabase dashboard → SQL Editor)

-- Refresh materialised view every 5 minutes
SELECT cron.schedule(
  'refresh-map-pins',
  '*/5 * * * *',
  $$REFRESH MATERIALIZED VIEW CONCURRENTLY mv_active_listing_pins;$$
);

-- Expire unconfirmed bookings after 24 hours (host didn't respond)
SELECT cron.schedule(
  'expire-pending-bookings',
  '0 * * * *',  -- every hour
  $$
    UPDATE bookings
    SET status = 'cancelled_by_platform',
        cancellation_reason = 'other',
        cancellation_note = 'Host did not respond within 24 hours'
    WHERE status = 'pending'
      AND created_at < NOW() - INTERVAL '24 hours';
  $$
);

-- Anonymise deleted user PII after 30-day cooling period
SELECT cron.schedule(
  'anonymise-deleted-users',
  '0 2 * * *',  -- 2am daily
  $$
    UPDATE users
    SET full_name = 'Deleted User',
        email = 'deleted_' || id || '@zipgrid.internal',
        phone = NULL,
        avatar_url = NULL
    WHERE deleted_at < NOW() - INTERVAL '30 days'
      AND full_name != 'Deleted User';
  $$
);

-- Purge session meter values older than 24 months
SELECT cron.schedule(
  'purge-old-meter-values',
  '0 3 1 * *',  -- 3am on 1st of each month
  $$
    DELETE FROM session_meter_values
    WHERE recorded_at < NOW() - INTERVAL '24 months';
  $$
);
```

### Backup Strategy

| Backup Type | Frequency | Retention | Method |
|-------------|-----------|-----------|--------|
| Continuous WAL archiving | Real-time | 7 days | Supabase built-in |
| Daily snapshot | 2am UTC | 30 days | Supabase built-in |
| Weekly snapshot | Sunday 3am | 3 months | Supabase built-in |
| Monthly snapshot | 1st of month 4am | 1 year | Supabase built-in |
| Pre-migration snapshot | Before each migration | 90 days | Manual (`pg_dump`) |

### Read Replica (Phase 2)

When MAU > 10,000, add a Supabase read replica for:
- Analytics queries (host earnings reports, KPI dashboard)
- Marketplace search
- Audit log reads

### CI Pipeline (Every PR)

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main, staging]

jobs:
  lint-typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run typecheck          # tsc --noEmit
      - run: npm run lint               # ESLint

  test-unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run test:unit          # Vitest --run

  test-integration:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgis/postgis:16-3.4
        env:
          POSTGRES_DB: zipgrid_test
          POSTGRES_PASSWORD: testpass
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run db:migrate:test    # Apply migrations to test DB
      - run: npm run test:integration   # Vitest integration tests

  security-audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm audit --audit-level=high  # Fail on high+ vulnerabilities

  preview-deploy:
    runs-on: ubuntu-latest
    needs: [lint-typecheck, test-unit, test-integration]
    steps:
      - uses: actions/checkout@v4
      - uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
```

### Production Deployment Pipeline

```yaml
# .github/workflows/deploy-production.yml
name: Deploy Production

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production    # Requires manual approval from protected environment
    steps:
      - uses: actions/checkout@v4

      - name: Run DB migrations
        run: npx drizzle-kit migrate
        env:
          DATABASE_URL: ${{ secrets.PROD_DIRECT_DATABASE_URL }}

      - name: Deploy to Vercel (production)
        uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-args: '--prod'

      - name: Restart Railway services
        run: |
          railway up --service ocpp-service
          railway up --service ai-service
        env:
          RAILWAY_TOKEN: ${{ secrets.RAILWAY_TOKEN }}

      - name: Post-deploy smoke tests
        run: npm run test:smoke          # 3 critical path tests against production

      - name: Notify Slack
        uses: slackapi/slack-github-action@v1
        with:
          payload: '{"text": "✅ Production deploy complete — ${{ github.sha }}"}'
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_DEPLOY_WEBHOOK }}
```

### Branch Protection Rules (GitHub)

- `main`: Require 1 PR review · All CI checks pass · No direct push · Linear history
- `staging`: Require all CI checks pass · No direct push to staging from feature branches

## 7. Database Migration Strategy

Migrations use **Drizzle ORM** with the `drizzle-kit` CLI.

```bash
# Generate a new migration from schema changes
npx drizzle-kit generate

# Apply migrations to staging
DATABASE_URL=$STAGING_DIRECT_URL npx drizzle-kit migrate

# Apply migrations to production (run in CI after approval)
DATABASE_URL=$PROD_DIRECT_URL npx drizzle-kit migrate
```

### Migration Safety Rules

1. **Always backward-compatible** — new columns must have defaults or be nullable
2. **Never rename columns in a single migration** — add new column, migrate data, drop old column in 3 separate deploys
3. **Never drop columns without a deprecation period** — mark as deprecated in schema comment for one deploy cycle first
4. **Large table migrations** — use `ADD COLUMN ... DEFAULT` (fast in Postgres 11+, no table lock)
5. **Index creation** — always `CREATE INDEX CONCURRENTLY` to avoid table locks in production

| **Supabase Dashboard** | DB connections, slow queries, storage | Dashboard only |

| **Stripe Dashboard** | Payment success/failure rates | Email + Slack |
| **PostHog** | User behaviour, funnels, feature flags | Dashboard only |

### Critical Alert Thresholds

| Metric | Warning | Critical | Action |
|--------|---------|----------|--------|
| API error rate | > 0.5% | > 2% | Page on-call; check Sentry |
| API p95 latency | > 500ms | > 2000ms | Check DB slow queries; Redis miss rate |
| OCPP service offline | — | > 30s | Auto-restart; alert ops |
| DB connection pool | > 70% | > 90% | Scale read replica |
| Redis memory | > 70% | > 90% | Review cache TTLs; scale |
| Failed Stripe payments | > 3% | > 10% | Alert payments team |
| Active sessions without heartbeat | > 10 | > 50 | OCPP health check |
| Sentry error volume | > 50/hr | > 200/hr | Investigate and patch |

### On-Call Rotation (Phase 1)

Until the team is large enough for a formal rota, the on-call model is:

- **Primary:** Lead backend engineer
- **Secondary (escalation):** Founder/CTO
- **Response SLA:** P1 (platform down) < 15 minutes · P2 (partial outage) < 1 hour · P3 (degraded) < 4 hours
- **Alerting tool:** PagerDuty (free tier for small team) or Opsgenie

## 9. Disaster Recovery

### Recovery Objectives

| Scenario | RTO (Recovery Time) | RPO (Data Loss) |
|----------|--------------------|-----------------| 
| Vercel deployment rollback | < 5 minutes | 0 (instant rollback) |
| Railway service restart | < 2 minutes | 0 (stateless) |
| Supabase point-in-time restore | < 30 minutes | < 1 minute (WAL) |
| Full region failure | < 4 hours | < 5 minutes |
| Data corruption | < 2 hours | < 24 hours (daily snapshot) |

### Rollback Procedures

**Vercel rollback (30 seconds):**
```bash
vercel rollback [deployment-url]
```

**Railway rollback:**
```bash
railway rollback --service ocpp-service
railway rollback --service ai-service
```

**Database rollback:**
```bash
# Point-in-time restore via Supabase dashboard
# Select snapshot timestamp → restore to new instance → promote
```

**Migration rollback:**
All migrations must have a corresponding `down` migration. Run before reverting application code.
