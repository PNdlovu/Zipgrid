## 1. Business Continuity Philosophy

Zipgrid is a real-time platform. An active charging session represents a driver physically connected to a charger — their vehicle cannot move until the session ends cleanly. A platform outage during an active session is not merely an inconvenience; it may strand a driver, leave a charger locked, and trigger a financial dispute. Every BCP decision is made with this reality in mind.

**Core principle:** OCPP-connected chargers are autonomous once a session starts. Even if the Zipgrid platform goes completely offline, a charging session that has already begun continues safely at the hardware level. The BCP therefore focuses on: (1) preventing outages, (2) minimising recovery time, and (3) protecting financial and session data.

## 3. Architecture Resilience

### 3.1 Railway Service Configuration

All Railway services are configured with:

```toml
[deploy]
  restartPolicyType = "ON_FAILURE"
  restartPolicyMaxRetries = 10
  healthcheckPath = "/health"
  healthcheckTimeout = 30
  healthcheckInterval = 10
```

Auto-restart handles the majority of transient failures (OOM, unhandled exception, network blip) without human intervention. Railway's health check system detects unhealthy instances and replaces them automatically.

### 3.2 Service Redundancy

| Service | Min Replicas | Auto-scale Trigger | Failover Behaviour |
|---------|-------------|-------------------|-------------------|
| Next.js API | 2 | CPU > 70% | Railway load-balances across replicas |
| OCPP Service | 2 | WS connections > 5,000/instance | Chargers reconnect to healthy instance |
| AI/Voice Service | 2 | CPU > 70% | Requests routed to healthy instance |
| PostgreSQL | 1 primary + 1 read replica | Always on | Read replica auto-promoted on primary failure |
| Redis | 1 (Upstash serverless) | Auto-scales | Upstash handles availability |

### 3.3 Database High Availability

Railway PostgreSQL provides:
- **WAL (Write-Ahead Logging) archiving** — continuous backup; RPO < 1 minute
- **Point-in-time restore (PITR)** — restore to any second within the retention window
- **Daily snapshots** — retained 30 days
- **Read replica** — promotes to primary automatically on primary failure (< 30-second promotion time)
- **Connection pooling via PgBouncer** — prevents connection exhaustion during traffic spikes

### 3.4 OCPP Session Resilience

This is the most critical resilience scenario — a charger is mid-session when the platform goes down.

**OCPP hardware behaviour:**
- OCPP chargers have a configurable `ConnectionTimeOut` — if the Central System goes offline, the charger continues the active session independently
- `StopTransactionOnEVSideDisconnect = true` ensures the charger handles disconnection safely without platform input
- When the Central System reconnects, chargers send a queued `StopTransaction` with final meter reading

**Platform recovery on reconnect:**
1. OCPP service restarts → chargers reconnect via WebSocket auto-reconnect (60-second retry interval)
2. Central System checks DB for sessions with status `charging` and no recent heartbeat
3. Sends `TriggerMessage: StatusNotification` to each charger to get current state
4. Reconciles meter readings from reconnect data with DB records
5. Captures any outstanding payment based on recovered meter stop value

### 4.1 Database Backups

| Backup Type | Frequency | Retention | Storage | Tested |
|-------------|-----------|-----------|---------|--------|
| WAL continuous | Real-time | 7 days | Railway (Amsterdam) | Monthly restore test |
| Daily snapshot | 2am UTC | 30 days | Railway (Amsterdam) | Monthly restore test |
| Weekly snapshot | Sunday 3am | 6 months | Railway (Frankfurt mirror) | Quarterly |
| Monthly snapshot | 1st 4am | 2 years | Cloudflare R2 (EU) | Bi-annually |
| Pre-migration manual | Before each migration | 90 days | Railway + R2 | Per event |

### 4.2 Media Backups

Cloudflare R2 provides:
- **Geo-redundant storage** — objects replicated across EU availability zones automatically
- **Versioning** — previous versions of overwritten objects retained 30 days
- No manual backup required for media

### 4.3 Code & Configuration Backups

- Source code: GitHub (EU data residency) — inherently versioned
- Infrastructure-as-code: `railway.toml` files committed to repository
- Environment variables: documented in LastPass / 1Password Team vault (not in source control)
- DNS configuration: Cloudflare — backed up as Terraform config (Phase 2)

## 5. Failover Procedures

### 5.1 Database Primary Failure

```
DETECTION: Railway health check fails on primary PostgreSQL
           + PgBouncer reports connection errors
           + Sentry alerts: "DB connection refused"
           
AUTOMATIC: Railway promotes read replica to primary (< 30 seconds)
           New connection string auto-configured via Railway's internal DNS
           
MANUAL VERIFICATION (on-call engineer):
  1. Confirm new primary is accepting writes:
     psql $NEW_PRIMARY_URL -c "SELECT pg_is_in_recovery();"  -- should return 'f'
  2. Confirm application is reconnecting:
     Check Railway logs for "Database connection restored"
  3. Spin up new read replica on Frankfurt:
     railway volume fork --region eu-central
  4. Update status page: "Database failover completed — all services normal"
  
POST-FAILOVER:
  - Investigate cause of primary failure
  - Restore geo-redundant replica within 4 hours
  - Post-mortem within 48 hours
```

### 5.2 Railway Regional Failure (Amsterdam)

Full `eu-west` region failure is unlikely but possible (AWS eu-west-1 has failed historically).

```
DETECTION: All Railway eu-west services unreachable
           Cloudflare health checks failing on all endpoints
           
TRIGGER: > 15 minutes of complete regional unavailability
         On-call engineer + Founder notified via PagerDuty

FAILOVER PROCEDURE (< 4 hours total):

Step 1 (0–30 min): Assessment
  - Confirm this is a regional failure, not a Railway-wide issue
  - Check Railway status page: status.railway.app
  - Check if DB data is accessible via Railway's failover tools

Step 2 (30–90 min): Database restore in Frankfurt
  - Restore latest snapshot to Railway eu-central (Frankfurt)
  - Verify data integrity: row counts on key tables
  - Update connection strings in Frankfurt environment variables

Step 3 (60–120 min): Deploy services to Frankfurt
  - railway up --region eu-central (all services)
  - Run smoke tests against Frankfurt endpoints
  - OCPP Central System online — chargers will reconnect

Step 4 (120–180 min): DNS cutover
  - Cloudflare DNS: point zipgrid.co.uk A record to Frankfurt IP
  - Propagation: < 5 minutes (Cloudflare proxied)
  - Verify map search, booking, and session endpoints working

Step 5 (180–240 min): Communication
  - Update status page: services restored in Frankfurt
  - Email to affected users: "Platform restored — your data is safe"
  - Investigate session data for any incomplete transactions during outage

Step 6 (post-recovery): Return to Amsterdam
  - When Amsterdam recovers, sync data back
  - Restore Amsterdam as primary
  - Frankfurt as permanent failover standby
```

### 5.3 Stripe Outage

```
DETECTION: Stripe dashboard shows incident
           Payment success rate drops below 90%
           
IMMEDIATE ACTIONS:
  1. Disable new bookings at application level (feature flag in admin panel)
  2. Post status page update: "Payment processing temporarily unavailable"
  3. Active sessions: continue — payment captured when Stripe recovers
  4. Notify support team to handle incoming driver questions

RECOVERY:
  - Monitor status.stripe.com for resolution
  - When Stripe recovers: re-enable bookings (feature flag)
  - Process any queued PaymentIntent captures
  - Contact affected users with apology + goodwill Wallet credit (configurable)

NEVER during a Stripe outage:
  - Attempt manual payment collection outside Stripe
  - Store card details to "try later"
  - Grant free sessions without a recovery plan
```

```
IMMEDIATE RESPONSE TEAM:
┌─────────────────────────────────────────────────────┐
│  INCIDENT COMMANDER: On-call Engineer               │
│  Owns the recovery. Makes all technical decisions.  │
├─────────────────────────────────────────────────────┤
│  COMMUNICATIONS LEAD: Founder / Product             │
│  Owns status page, user comms, stakeholder updates. │
├─────────────────────────────────────────────────────┤
│  TECHNICAL SUPPORT: Second on-call Engineer         │
│  Executes recovery steps under IC direction.        │
└─────────────────────────────────────────────────────┘

COMMUNICATION CADENCE during P1:
  T+0:     Incident acknowledged in Slack #incidents
  T+5:     Status page updated: "Investigating"
  T+15:    Internal update: diagnosis known?
  T+30:    Status page: ETA for resolution
  T+60:    User email if > 1 hour downtime
  T+every 30: Status page update until resolved
  T+resolve: Status page: resolved + root cause summary
  T+48hrs:   Post-mortem published
```

### 7.2 Vendor Concentration Risk

| Risk | Vendor | Mitigation |
|------|--------|-----------|
| Payment processor | Stripe only | Adyen as documented backup — integration scoped in Phase 2 |
| Hosting | Railway only | All services containerised (Docker); can run on AWS/GCP in < 8 hours |
| AI provider | OpenAI only | Anthropic Claude as documented fallback — same API interface |
| Maps | Mapbox only | OpenStreetMap + Leaflet.js as free fallback for critical map functions |
| Voice STT | Web Speech + Whisper | Deepgram as documented backup STT provider |

### 7.3 Financial Continuity

- **Operating runway target:** 6 months cash reserve at all times
- **Stripe payouts:** Weekly disbursement to business bank account
- **Host payouts:** Held in Stripe — never at risk if platform bank account is inaccessible
- **Emergency spending authority:** Up to £5,000 without board approval for incident response
- **Business interruption insurance:** To be assessed with insurance broker (covers revenue loss during outage)
