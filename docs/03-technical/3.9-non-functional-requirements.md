## 3. Scalability

### 3.1 Horizontal Scaling

Every service must scale horizontally (add more instances) without code changes:

| Service | Scaling Method | State Management |
|---------|--------------|-----------------|
| Next.js API | Railway auto-scale (stateless) | No state in memory; all state in DB/Redis |
| OCPP Service | Manual scale (Railway) | Connection affinity via Redis pub/sub |
| AI/Voice Service | Railway auto-scale | Stateless request/response |
| PostgreSQL | Read replicas for read scaling | Primary handles writes only |
| Redis | Upstash serverless auto-scale | Built-in |

### 3.2 Database Scalability

| Threshold | Action |
|-----------|--------|
| Query p95 > 100ms | Add index or optimise query |
| Connection pool > 80% | Add read replica |
| DB storage > 70% | Increase volume |
| Row count on hot tables > 100M | Implement partitioning |
| `session_meter_values` > 500M rows | Archive rows > 24 months to cold storage |

### 3.3 Multi-Tenancy

The platform is designed for multi-tenant white-labelling (Phase 4). Key decisions made now:
- `tenant_id` column on all user-facing tables (nullable at launch — single tenant)
- Row-Level Security (RLS) policies reference `tenant_id` where present
- API routes are tenant-aware in their middleware layer
- Mapbox styles configurable per tenant
- Email templates brandable per tenant
- This adds < 2% overhead at single-tenant scale

## 4. Security Requirements

### 4.1 Authentication & Authorisation

| Requirement | Implementation |
|-------------|---------------|
| All API endpoints authenticated | JWT Bearer token required; middleware on all routes |
| Short-lived access tokens | 15-minute TTL |
| Refresh token rotation | Single-use; previous token invalidated on use |
| Refresh token revocation | Redis blocklist; revoked on logout and suspicious activity |
| Admin MFA | TOTP mandatory for all admin accounts |
| User MFA | TOTP optional (enforced for high-value hosts Phase 2) |
| Brute force protection | 5 failed attempts → 15-minute account lock (Redis counter) |
| Credential stuffing protection | Cloudflare Turnstile on all auth forms |
| Session binding | JWT tied to device fingerprint (IP + User-Agent hash) |
| Concurrent session limit | Max 5 active sessions per account (configurable) |

### 4.2 Data Security

| Requirement | Implementation |
|-------------|---------------|
| Encryption in transit | TLS 1.3 minimum on all connections (HTTPS + WSS) |
| Encryption at rest | AES-256 at database level (Railway provides this) |
| Field-level encryption | Access codes (gate codes) AES-256-GCM in application layer |
| Password storage | bcrypt cost factor 12 (never stored in plain text) |
| PII minimisation | Only collect data necessary for platform function |
| Card data | Never stored — Stripe.js isolates all card data |
| KYC documents | Never stored on Zipgrid servers — Stripe Identity retains |
| Secrets management | Railway environment variables — never in source code |
| Dependency scanning | Snyk in CI pipeline — fails build on critical vulnerabilities |
| SAST | GitHub CodeQL analysis on every PR |

### 4.3 Network Security

| Requirement | Implementation |
|-------------|---------------|
| DDoS protection | Cloudflare layer 3/4/7 protection |
| WAF | Cloudflare WAF — OWASP Top 10 rule set |
| Rate limiting | 100 requests/minute/user (authenticated); 20/minute (unauthenticated) |
| Bot management | Cloudflare Bot Management — blocks automated scraping |
| CORS | Strict allowlist — only zipgrid.co.uk origins |
| CSP headers | Strict Content Security Policy (see 3.5-security-privacy.md) |
| HSTS | 2-year max-age + preload |
| Security headers | X-Frame-Options: DENY; X-Content-Type-Options: nosniff |
| OCPP security | WSS + Basic Auth; rate-limited to 10 messages/second/charger |

| i18n framework | `next-intl` (Next.js native) |
| Translation files | JSON per locale: `/messages/en-GB.json`, `/messages/nl.json` |

| Pluralisation | ICU message format (handles irregular plurals per language) |

## 7. Reliability & Fault Tolerance

| Requirement | Implementation |
|-------------|---------------|
| Circuit breaker | All external API calls wrapped in circuit breaker (fail fast after 5 consecutive failures) |
| Retry logic | Idempotent operations: max 3 retries with exponential backoff |
| Timeout enforcement | All external API calls: 5-second timeout; OCPP commands: 30-second timeout |
| Graceful degradation | Map falls back to OpenStreetMap if Mapbox fails; voice falls back to text if Whisper fails |
| Queue-based notifications | Push/email/SMS go through a job queue — failure retried up to 3 times |
| Idempotency keys | All Stripe API calls include idempotency keys — safe to retry |
| Dead letter queue | Failed notification jobs moved to DLQ after 3 retries; ops alerted |
| Health checks | Every service exposes `GET /health` returning 200 with service status |
