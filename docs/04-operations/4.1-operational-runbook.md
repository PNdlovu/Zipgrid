## 1. Incident Severity Levels

| Severity | Definition | Response Time | Example |
|----------|-----------|---------------|---------|
| **P1 — Critical** | Platform completely down or data loss occurring | 15 minutes | API returning 500, DB unreachable, OCPP service offline |
| **P2 — High** | Core feature broken for all users | 1 hour | Bookings failing, payments not processing, sessions stuck |
| **P3 — Medium** | Feature broken for subset of users, workaround exists | 4 hours | Voice commands failing, specific charger brand offline |
| **P4 — Low** | Minor degradation, no immediate business impact | Next business day | Slow report generation, cosmetic UI bug |

## 2. Incident Response Procedure

### Step 1 — Detect

Alerts come from:
- Sentry (runtime errors)
- Vercel Monitoring (error rate / latency spikes)
- Railway (service down / health check failed)
- Supabase (DB connection exhaustion)
- User reports via support@zipgrid.co.uk or in-app "Report a Problem"

### Step 2 — Acknowledge

- On-call engineer acknowledges the alert in PagerDuty within the SLA window
- Posts to Slack **#incidents** channel: `🔴 P[N] INCIDENT — [brief description] — investigating`
- If P1/P2: immediately notify Founder

### Step 3 — Assess

Within the first 5 minutes, answer:
1. What is broken? (which service / feature)
2. How many users affected? (check PostHog active user count)
3. Is data being lost or corrupted? (check Supabase logs)
4. Is there an active charging session affected? (check `charging_sessions` where `status = 'charging'`)
5. Is there a financial transaction in flight? (check `transactions` where `status = 'hold_placed'`)

### Step 4 — Communicate

**P1/P2:** Post a status page update at `status.zipgrid.co.uk` within 15 minutes:
> "We are currently experiencing issues with [feature]. Our team is investigating. We will update every 30 minutes."

**Notify affected users proactively** if an active charging session is impacted:
- Push notification: "We're experiencing a technical issue. Your session data is safe. Contact support if needed."

### Step 5 — Resolve

Follow the relevant runbook section below. After each action taken, post an update to **#incidents**.

### Step 6 — Post-Incident Review

All P1/P2 incidents require a written post-mortem within 48 hours:
- **Template:** Timeline · Root cause · Impact · Resolution · Preventive actions with owners and dates
- Stored in: `docs/04-operations/post-mortems/YYYY-MM-DD-[incident].md`
- Reviewed in weekly ops meeting

## 3. Service-Specific Runbooks

### 3.1 API / Next.js Application Down

**Symptoms:** All API routes returning 500; Vercel deployment shows errors

**Diagnosis steps:**
```bash
# Check Vercel function logs
vercel logs --app zipgrid --since 30m

# Check Sentry for error spike
# → app.sentry.io → Zipgrid project → Issues → Last 30 minutes

# Check if it's a deployment issue
vercel rollback   # lists recent deployments
```

**Resolution — Bad deploy:**
```bash
vercel rollback [previous-deployment-url]
# Takes ~30 seconds. Verify by hitting GET /api/v1/health
```

**Resolution — DB connection issue:**
```bash
# Check Supabase dashboard → Database → Connections
# If pool exhausted: restart pgBouncer via Supabase dashboard
# Temporary: increase pool size in connection string
# ?pgbouncer=true&connection_limit=20  →  connection_limit=30
```

**Resolution — Environment variable missing:**
```bash
# Check Vercel dashboard → Settings → Environment Variables
# Common: new env var added in PR but not added to production
# Fix: add variable, trigger redeploy
vercel --prod  # force production redeploy
```

### 3.2 OCPP Service Down

**Symptoms:** All chargers show "Offline"; sessions cannot be started; OCPP health check failing

**Immediate actions:**
1. Check if any active charging sessions exist:
```sql
SELECT COUNT(*) FROM charging_sessions WHERE status IN ('charging', 'authorized');
```
If sessions are active: they will continue charging safely — OCPP chargers are autonomous once started. The session data will sync when service reconnects.

2. Check Railway dashboard → ocpp-service → Logs

**Common causes and fixes:**

| Cause | Fix |
|-------|-----|
| OOM (out of memory) | Scale Railway instance memory; restart |
| Too many open WS connections | Scale to 2 instances; check for WS leaks in logs |
| Redis connection lost | Check Upstash dashboard; restart service |
| Railway instance restart (deploy) | Service auto-restarts; chargers reconnect in 30-60s |

```bash
# Force restart via Railway CLI
railway restart --service ocpp-service

# Check connection count
curl -H "Authorization: Bearer $OCPP_INTERNAL_SECRET" \
  https://ocpp-internal.railway.app/health
# → { "connections": 0 }  means all chargers disconnected
```

**Charger reconnection:** OCPP chargers have built-in reconnection logic. Most reconnect within 60 seconds of service restart. Monitor via:
```sql
SELECT COUNT(*) FROM charger_listings
WHERE ocpp_charge_point_id IS NOT NULL
-- check Redis: ocpp:connection:{chargePointId} keys
```

### 3.3 Stuck Charging Session

**Symptoms:** Session status is `charging` but no recent MeterValues; driver reports charger appears stopped; no `StopTransaction` received

**Diagnosis:**
```sql
-- Find sessions that haven't received a meter update in > 10 minutes
SELECT
  cs.id,
  cs.ocpp_charge_point_id,
  cs.ocpp_transaction_id,
  cs.started_at,
  MAX(smv.recorded_at) AS last_meter_at,
  NOW() - MAX(smv.recorded_at) AS gap
FROM charging_sessions cs
LEFT JOIN session_meter_values smv ON smv.session_id = cs.id
WHERE cs.status = 'charging'
GROUP BY cs.id, cs.ocpp_charge_point_id, cs.ocpp_transaction_id, cs.started_at
HAVING NOW() - MAX(smv.recorded_at) > INTERVAL '10 minutes'
   OR MAX(smv.recorded_at) IS NULL;
```

**Resolution options (in order):**

1. **Trigger status check** — request a fresh status from charger:
```bash
POST /ocpp/trigger-message
{ "chargePointId": "ZIPGRID-LON-0042", "message": "StatusNotification" }
```

2. **Remote stop** — if charger is reachable, send RemoteStop:
```bash
POST /ocpp/remote-stop
{ "sessionId": "uuid" }
```

3. **Manual session close** — if charger is unreachable and session clearly ended:
```sql
-- Use last known meter value for energy calculation
UPDATE charging_sessions
SET status = 'timed_out',
    ended_at = NOW(),
    meter_stop_wh = (
      SELECT energy_wh FROM session_meter_values
      WHERE session_id = 'uuid'
      ORDER BY recorded_at DESC LIMIT 1
    ),
    stop_reason = 'Other'
WHERE id = 'uuid';
```
Then trigger Stripe capture via admin panel with the partial session value.

4. **Notify driver** — push notification + email explaining the situation; offer full refund if session didn't complete properly.

### 3.4 Payment Failure / Stripe Issues

**Symptoms:** Bookings failing at payment step; Stripe dashboard showing elevated error rate

**Diagnosis:**
```bash
# Check Stripe dashboard → Developers → Logs → Filter: errors, last 1 hour
# Common error codes:
# card_declined      → Driver's card declined (contact driver)
# insufficient_funds → Driver's card has insufficient funds
# stripe_error       → Stripe platform issue (check status.stripe.com)
```

**If Stripe platform is down:**
- Check `status.stripe.com`
- Bookings will fail — communicate on status page
- Do NOT attempt to retry payments manually during an outage
- Queue affected bookings for retry when Stripe recovers

**Stuck PaymentIntent (hold placed, never captured):**
```sql
-- Find holds older than 7 days not yet captured
SELECT t.id, t.stripe_payment_intent_id, t.created_at
FROM transactions t
WHERE t.status = 'hold_placed'
  AND t.created_at < NOW() - INTERVAL '7 days';
```
Stripe automatically releases uncaptured PaymentIntents after 7 days. If session completed but capture failed: trigger manual capture via admin panel → Payments → Transactions.

### 3.5 Database Emergency

**Symptoms:** DB queries timing out; `connection refused` errors; Supabase reporting high load

**Immediate actions:**

1. **Connection pool exhausted:**
```bash
# Check active connections
SELECT COUNT(*), state FROM pg_stat_activity GROUP BY state;

# Kill idle connections
SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE state = 'idle'
  AND query_start < NOW() - INTERVAL '5 minutes';
```

2. **Long-running query blocking:**
```bash
# Find blocking queries
SELECT pid, now() - pg_stat_activity.query_start AS duration, query, state
FROM pg_stat_activity
WHERE state != 'idle'
  AND now() - pg_stat_activity.query_start > INTERVAL '30 seconds'
ORDER BY duration DESC;

# Terminate if blocking production
SELECT pg_terminate_backend(pid) WHERE pid = [blocking_pid];
```

3. **Disk full:**
```bash
# Check Supabase dashboard → Storage → Database
# If > 90%: run VACUUM, delete old meter_values (per retention policy)
DELETE FROM session_meter_values
WHERE recorded_at < NOW() - INTERVAL '24 months';
VACUUM ANALYZE session_meter_values;
```

4. **Point-in-time restore** (last resort):
- Supabase dashboard → Database → Backups → Point-in-time restore
- Restore to new instance; test; promote
- RTO: ~30 minutes. RPO: < 1 minute (WAL archiving)

### 3.6 Data Breach Response

**If a potential data breach is detected:**

1. **Contain immediately:** Revoke compromised credentials; isolate affected service
2. **Assess scope:** What data? How many users? How was it accessed?
3. **Preserve evidence:** Do not delete logs; capture screenshots; document timeline
4. **Notify Founder within 1 hour** — legal obligations follow
5. **ICO notification** — required within **72 hours** if likely to result in risk to individuals
6. **User notification** — if high risk to rights/freedoms, notify affected users promptly
7. **Engage solicitor** — for GDPR breach response guidance

See `3.5-security-privacy.md` Section 7 for full breach protocol.
