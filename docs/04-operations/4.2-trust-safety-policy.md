## 1. Trust & Safety Philosophy

Zipgrid is a two-sided marketplace built on trust. A homeowner is opening their private property to a stranger. A driver is handing over their payment details and vehicle to a private electricity supply. Every feature, policy, and enforcement action is designed to make that trust well-placed.

Trust operates at four levels:
1. **Identity trust** — we know who the people on the platform are
2. **Financial trust** — money moves correctly and disputes are resolved fairly
3. **Physical trust** — sessions are safe, property is respected, incidents are handled
4. **Data trust** — personal information is protected and used only as stated

## 2. Identity Verification (KYC)

### 2.1 Requirements by Role

| Action | ID Verification Required? | KYC Level |
|--------|--------------------------|-----------|
| Register (driver only) | No | None |
| Make a booking (driver) | No | Email verified |
| List a charger (host) | **Yes** | Full KYC |
| Receive payouts (host) | **Yes** | Full KYC + bank account |
| Sell on marketplace (vendor) | **Yes** | Full KYC + business registration |
| Book an installer job (driver) | No | Email verified |
| Receive installer payments | **Yes** | Full KYC + bank account |

### 2.2 KYC Process

Full KYC is handled by **Stripe Identity** — documents never pass through Zipgrid servers.

**Steps:**
1. Host taps "Set up payouts" or "Publish listing"
2. Stripe Identity SDK opens (in-app web view)
3. Host submits: government-issued photo ID (passport, driving licence, national ID) + selfie
4. Stripe runs automated document verification + liveness check
5. Result returned to Zipgrid webhook: `verified` or `failed`
6. On `verified`: `users.kyc_status` updated, `host_profiles.identity_verified` set to `true`

**Timeframe:** Automated verification typically completes in under 2 minutes. Manual review cases (older documents, partial obstructions) may take up to 24 hours.

**KYC failure handling:**
- User is notified with the reason (document unclear, name mismatch, liveness failed)
- User can retry up to 3 times
- After 3 failures: account flagged for manual review by platform ops team
- Host listings remain in draft status until KYC passes

### 2.3 Business Verification (Commercial Hosts)

In addition to personal KYC, commercial hosts must provide:
- Companies House registration number (verified via Companies House API)
- VAT number (verified via HMRC VIES API — optional if below VAT threshold)
- Business bank account via Stripe Connect

### 2.4 Continuous Monitoring

- If Stripe Identity flags a user post-verification (e.g. document reported stolen): account suspended pending investigation
- Accounts with >3 chargebacks in 90 days: flagged for identity re-verification

## 3. Host Verification & Listing Safety

### 3.1 Listing Safety Checklist

Before a listing goes live, the host must confirm:

```
□ My charger is less than 10 years old
□ My charger was installed by a qualified electrician
□ My charger has RCD/GFCI (residual current device) protection
□ The charging cable is undamaged with no exposed wiring
□ The charging area is free from trip hazards
□ I have read and accept the Host Safety Requirements
□ I understand I must notify my home insurer of commercial use
□ I accept the Host Terms and Protection (/legal/host-terms)
```

**Self-certification model (launch):** Hosts self-certify at listing creation. False self-certification that results in an incident leads to removal of the listing and may void the host's own insurance.

**Inspection model (Phase 2):** High-volume hosts (> 50 sessions/month) or listings with repeat faults may be required to submit a photo inspection or book a certified installer survey.

### 3.2 Listing Moderation

All new listings go through an automated + manual review before activation:

**Automated checks:**
- Address validation (geocoding must resolve to a real UK address)
- Photo content moderation (no inappropriate images — via Google Vision API or similar)
- Pricing sanity check (flag if > 3× median for the area)
- Duplicate listing detection (same OCPP chargePointId cannot appear twice)

**Manual review triggers:**
- First listing from any new host (reviewed within 24 hours)
- Listings reported by users
- Listings in areas with a prior incident
- Listings where automated checks flagged anomalies

**Listing status flow:**
```
draft → [host submits] → active (instant book hosts)
draft → [host submits] → under_review → active (manual review hosts)
active → [report received] → under_review
under_review → [admin approves] → active
under_review → [admin rejects] → deactivated
```

## 4. Driver Verification & Trust

### 4.1 Trust Levels

| Level | How Earned | Privileges |
|-------|-----------|-----------|
| **Standard** | Email verified | Can browse and book |
| **Phone Verified** | Phone OTP confirmed | Slightly higher booking limits |
| **Trusted Driver** | 10+ completed sessions · 4.5+ rating · 0 incidents | Instant booking at all listings; unlocked by hosts for gate codes without prior contact |
| **Verified ID** | Stripe Identity completed (optional for drivers) | Trust badge on profile; hosts may require this for high-value listings |

### 4.2 Booking Restrictions

New drivers (< 3 sessions) are subject to:
- Cannot book sessions > 8 hours on first booking
- Cannot book DC Fast Charge sessions (if added in Phase 2)
- Host may restrict their listing to Trusted Drivers only

### 4.3 Driver Violation Tracking

| Violation | Points | Consequence |
|-----------|--------|------------|
| Overstay idle fee (first time) | 0 | Warning notification |
| Overstay idle fee (repeat: 3+) | 1 | Host can block driver |
| No-show (booking confirmed, never arrived) | 2 | Warning; refund withheld |
| Confirmed property damage | 5 | Account suspended |
| Fraudulent dispute/chargeback | 5 | Account suspended |
| Identity fraud | Instant | Permanent ban |
| Threatening or abusive behaviour | Instant | Permanent ban |

**Thresholds:** 3 points in 90 days → temporary suspension (14 days) · 6 points ever → permanent ban

## 5. Reviews & Ratings

### 5.1 Review Eligibility

A review can only be submitted when:
- The booking status is `completed`
- The review is submitted within **14 calendar days** of session end
- The reviewer was the driver or host on that booking (no third parties)

### 5.2 Blind Review System

Reviews are mutually blind until both parties submit, preventing retaliatory ratings:

```
Host submits review (status: pending)
Driver submits review (status: pending)
  → Both reviews revealed simultaneously (status: published)

OR:

One party submits; the other does not within 14 days
  → Submitting party's review published after 14-day window
  → Non-submitting party loses their opportunity
```

### 5.3 Review Integrity

**Prohibited review content:**
- Personal attacks, discriminatory language, or threats
- Competitor promotion or spam
- Factually false statements (demonstrably untrue claims)
- Private personal information about the other party
- Content relating to disputes still under investigation

**Review moderation triggers:**
- Contains profanity filter matches → held for manual review
- Contains a name that matches another user's real name → held for review
- Rating is 1 star + contains no comment → prompt for more detail (not blocked)
- Reported by the other party → flagged, not auto-removed

**Manipulation prevention:**
- One review per booking, per side — cannot submit twice
- Review submission IP is logged — sockpuppet detection
- Reviews from users who have never completed a session are blocked
- Sudden spike in 5-star reviews for a listing → temporary hold for investigation

### 5.4 Rating Impact

- `charger_listings.average_rating` — updated by DB trigger on every published review
- `host_profiles.average_rating` — updated similarly
- `driver_profiles.violation_count` — updated on host review of driver (admin input only)
- Superhost eligibility: recalculated weekly by platform job

## 6. Incident Handling

> Updated October 3, 2026 to match the implemented Resolution Centre (`DisputeService`) and the insurance model in `5.1-insurance-liability.md` v0.2: **Zipgrid does not insure hosts or drivers**; it recovers damage from drivers at fault and supplies evidence to the parties' own insurers.

### 6.1 Incident Categories

Cases are opened in the Resolution Centre (`/help/resolution`) by **either party** to a booking, from the booking page or with the 8-character booking reference. The case is raised against the other party, who is notified and can add evidence.

| Category (`dispute_type`) | Examples | Remedy |
|----------|---------|------------------|
| `safety_incident` | Injury, electrical fault, fire, harassment | 999 first; 1-hour acknowledgement; parties' insurers for injury/fire; listing paused if hardware fault |
| `property_damage` | Driver damages charger, cable, gate, wall | Damage recovery from driver ≤ £1,000; above that, host's insurer |
| `session_fault` / `charger_unavailable` | Charger failed or inaccessible | Refund to driver |
| `billing` | Wrong amount charged | Refund to driver |
| `driver_behaviour` | Conduct of the other party | Warning, violation points, suspension |
| `other` | Anything else | Case by case |

### 6.2 Deadlines

| What | Deadline | Enforced by |
|------|----------|-------------|
| Driver reports a problem they caused or saw | Within 24 hours (Driver Responsibilities) | Policy |
| Host reports damage | Within 14 days of booking end | API rejects later reports (`REPORTING_WINDOW_CLOSED`); support can open late cases manually |
| Zipgrid acknowledges a safety case | 1 hour | `disputes.acknowledge_by`; overdue cases flagged at the top of `/admin/disputes` |
| Zipgrid acknowledges any other case | 24 hours | as above |
| Decision | Most cases 5 business days; damage claims 10 | Ops KPI |
| Other party responds | 14 days, then decided on the evidence available | Ops |
| Appeal | 14 days from decision, by email to support with the case number | Ops |

### 6.3 Incident Response Flow

```
1. Driver or host opens a case (Resolution Centre / booking page)
   → booking, vehicle and charging-session record captured automatically
     (times, energy, peak power, stop reason, fault codes) in disputes.session_snapshot
   → other party notified (in-app + email); acknowledgement deadline set

2. Acknowledge (admin "Acknowledge and start review"; any admin action counts)
   → safety cases first, then overdue acknowledgements

3. Evidence (both parties): photos, video, repair quote or invoice

4. Decision options:
   → Full or partial refund to driver (wallet or card)
   → Uphold host damage claim and charge the driver ≤ £1,000
       (needs host-raised property_damage case with evidence;
        collected wallet → saved card; credited to host in full, no commission;
        unpaid charge blocks the driver's new bookings)
   → Escalate (injury, fire, loss > £1,000): evidence package to the parties' insurers
   → No action (unfounded)
   → Account action (warning, violation points, suspension, ban)

5. Post-incident:
   → Outcome to both parties; damage charge notified to both
   → Listing reviewed / paused if hardware fault
   → Audit log entry
```

## 7. Escalation to insurers

Zipgrid holds no policy that pays hosts or drivers. These cases are escalated (status `escalated_to_insurer`) and the evidence package from `5.1` §3 is sent to whichever insurer is handling the claim:

| Trigger | Action |
|---------|--------|
| Personal injury | Escalate same day; host's public liability insurer; consider pausing listing |
| Fire or electrical fault | Escalate; pause listing pending inspection |
| Damage above £1,000 | Recover nothing through the platform; host claims via own insurer, who may pursue the driver |
| Police report number submitted | Escalate to Critical; cooperate with police requests |

Zipgrid's own corporate cover (CGL, PI, cyber) responds only to claims against Zipgrid itself — see `5.1` §5.

## 8. Prohibited Uses & Bans

### 8.1 Prohibited Listing Uses

- Listing chargers at addresses the host does not own or have permission to use
- Listing the same charger under multiple accounts
- Intentionally misrepresenting charger specifications, speed, or access
- Listing non-functional or permanently broken chargers
- Exploiting pricing to charge rates inconsistent with the listing (e.g. changing price during a booked session)

### 8.2 Prohibited Driver Behaviour

- Using access codes obtained from a booking to access a property outside booked hours
- Overstaying repeatedly to accrue idle fees that are then disputed
- Providing false vehicle details to gain access to charger types they cannot use
- Chargeback fraud (claiming non-delivery when session telemetry confirms completion)

### 8.3 Account Suspension Process

```
Violation detected (automated flag or human report)
  │
  ▼
Trust & Safety agent reviews evidence (within 24 hours for serious violations)
  │
  ├── Insufficient evidence → No action; note on file
  │
  ├── Policy violation confirmed → Warning issued (1st offence for minor violations)
  │
  └── Serious violation → Immediate suspension
        │
        ▼
      User notified by email with reason
      User can appeal within 14 days
        │
        ├── Appeal upheld → Account reinstated; correction noted
        └── Appeal rejected → Suspension maintained or permanent ban
```

### 8.4 Permanent Bans

Permanent bans are issued immediately for:
- Identity fraud or use of fraudulent KYC documents
- Physical assault or credible threats against another user
- Deliberate property damage
- Repeated serious violations after reinstatement

Permanently banned users cannot create new accounts. IP + device fingerprint blocking applied.

## 9. Data & Privacy in Trust Context

- Host's full address is **never shown** to drivers until booking is confirmed
- Driver's surname and contact details are **never shown** to hosts
- Access codes are **encrypted in DB** and only decrypted at booking confirmation
- After a session ends, access codes are **auto-invalidated** — old codes cannot be reused
- Resolution Centre cases and evidence (photos, session snapshot) are kept for 6 years after the case closes (limitation period for claims), then deleted
- If a user is banned, their data is retained per GDPR retention schedule but access is revoked

## ADDENDUM v0.2 — Safety Scoring Methodology
### Added: September 29, 2026 | Source: PRD Module M · Gap Analysis N8

> This addendum documents the Safety Score system — a composite 0–100 score displayed on every listing to signal physical safety to drivers and to auto-enforce minimum standards.

---

## 10. Listing Safety Score

### 10.1 Overview

Every active Zipgrid listing carries a **Safety Score** (0–100) calculated nightly from six weighted components. The score is displayed:

- On listing cards (compact: shield icon + number)
- On the listing detail page (full breakdown, visible to the host)
- In the host portal under "Listing health"

The score is the primary mechanism by which Zipgrid enforces hardware safety standards beyond the self-certification checklist.

---

### 10.2 Score Components

| Component | Weight | How Measured | Full Score Condition |
|-----------|--------|--------------|----------------------|
| **Charger age** | 20% | Host-declared installation year. Cross-checked with OCPP firmware date where available. | < 2 years old |
| **RCD protection** | 15% | Host confirms residual current device protection at listing creation | Confirmed present |
| **Electrician installed** | 15% | Host confirms professional installation (OZEV-approved or equivalent) | Confirmed yes |
| **OCPP fault rate** | 20% | Faults per 100 sessions (last 90 days) from OCPP telemetry. Only unresolved faults count. | 0 faults per 100 sessions |
| **Driver complaints** | 15% | Verified incident reports against this listing in the last 6 months (must be from a completed session on that listing — prevents false reports) | 0 complaints |
| **Platform inspection** | 15% | Manual flag set by Trust & Safety ops team after a physical or photo review | Inspection passed |

**Score calculation formula:**

```
overall_score = ROUND(
  (charger_age_score    × 0.20) +
  (rcd_protection_score × 0.15) +
  (electrician_score    × 0.15) +
  (fault_rate_score     × 0.20) +
  (complaints_score     × 0.15) +
  (inspection_score     × 0.15)
)
```

---

### 10.3 Score Bands

| Band | Range | Display | Automatic Action |
|------|-------|---------|-----------------|
| ✅ **Excellent** | 90–100 | Green shield | None |
| 🟡 **Good** | 70–89 | Amber shield | None |
| ⚠️ **Fair** | 50–69 | Orange shield | Warning badge displayed; host receives improvement suggestions |
| 🔴 **Needs attention** | < 50 | Red shield | **Listing auto-paused** pending host remediation |

---

### 10.4 Auto-Pause Behaviour

When a listing drops below 50:

1. Listing status is set to `under_review`
2. All pending bookings scheduled within the next 48 hours are cancelled (with full driver refund)
3. Host is notified by push + email with the specific component(s) causing the low score
4. Host can see the full breakdown and recommended actions in their portal
5. Listing cannot be re-activated by the host — requires Trust & Safety team review

**Re-activation process:**
1. Host resolves the identified issue (e.g. confirms RCD was installed, books an inspection)
2. Host submits a remediation request via the admin panel
3. Trust & Safety recalculates or manually overrides the score component
4. If score returns above 50, listing is reactivated

---

### 10.5 Score Calculation Schedule

- **Nightly job:** All active listings are recalculated daily at 02:00 UTC via `pg_cron`
- **On-demand:** Recalculated immediately after a new incident report or OCPP fault event
- **Host-triggered:** Host can request a recalculation after resolving a flagged issue (rate-limited to once per 24 hours)

---

### 10.6 Non-Gamesmanship Rules

The Safety Score is designed to be ungameable:

1. **Driver complaints require a completed session** on that listing — a driver who has never visited cannot file a complaint that affects the score
2. **OCPP fault data is read-only from telemetry** — hosts cannot self-declare that faults are resolved; the platform must see fault-free sessions
3. **Platform inspection is set exclusively by Trust & Safety ops** — hosts cannot influence it
4. **Score history is retained** — a host cannot reset their score by delisting and relisting the same charger (OCPP chargePointId is used to link history)

---

### 10.7 Host Improvement Guidance

When a listing has a non-excellent score, the host portal shows specific guidance:

| Low component | Suggested action |
|--------------|-----------------|
| Charger age < score | "Your charger is [X] years old. Consider upgrading to maintain your safety score." |
| RCD not confirmed | "Confirm your RCD protection in listing settings to add 15 points to your score." |
| No electrician install | "Add proof of professional installation. Book a certified installer via the Marketplace." |
| High OCPP fault rate | "Your charger has reported [N] faults in the last 90 days. Use the diagnostic tool to investigate." |
| Driver complaints | "You have received [N] verified complaints. Review your listing's access instructions and charger condition." |
| Not inspected | "Book a Zipgrid platform inspection to unlock the full 15 points for this component." |

---

### 10.8 Relationship to Insurance Coverage

- Zipgrid does not insure hosts (see `5.1` v0.2). The score is evidence: when a case is reviewed, a known safety deficiency (score below 70, or a failed checklist item) weighs against the host, and a fault in the host's own installation is excluded from damage recovery.
- A host's own insurer may apportion liability to the host for an incident caused by a known deficiency; the score history is part of the evidence package we provide.
- Deliberately false self-certification that contributes to an incident leads to removal of the host's listings.
