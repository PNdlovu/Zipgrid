## 1. Threat Landscape

Zipgrid operates in a financial marketplace with real money, real property access, and real energy. The fraud surface is wider than a typical app:

| Threat | Vector | Potential Impact |
|--------|--------|-----------------|
| Account takeover | Credential stuffing, phishing, session hijacking | Financial loss, property access theft |
| Identity fraud (KYC bypass) | Fake documents, synthetic identity | Fraudulent payouts, AML violations |
| Fake listings | Non-existent or misrepresented chargers | Chargebacks, reputation damage |
| Chargeback fraud | False "not received" claims on completed sessions | Revenue loss, Stripe dispute penalties |
| Impersonation | Fake Zipgrid communications (phishing) | User credential theft |
| OCPP command injection | Malicious actor hijacking charger control | Equipment damage, safety risk |
| Fake reviews | Sockpuppet accounts inflating/deflating ratings | Trust erosion |
| Payout fraud | Fake bank accounts, money mule activity | AML violations, financial loss |
| Promo abuse | Multiple accounts exploiting referral codes | Revenue leakage |
| Denial of service | Automated booking attacks, API flooding | Platform availability |

## 2. Account Takeover (ATO) Prevention

### 2.1 Detection Signals

The platform monitors for these signals on every authentication event:

```typescript
/**
 * @file auth-risk-engine.ts
 * @description Risk scoring for authentication events.
 * Combines multiple signals to assign a risk score.
 * High-risk logins require additional verification.
 */

type AuthRiskSignals = {
  ipAddress:        string
  userAgent:        string
  geoLocation:      { country: string; city: string }
  loginTime:        Date
  deviceFingerprint: string
  failedAttempts:   number       // in last 15 minutes
  newDevice:        boolean      // first login from this device fingerprint
  newLocation:      boolean      // first login from this country/city
  vpnDetected:      boolean      // Cloudflare VPN detection
  torDetected:      boolean
  knownBadIp:       boolean      // cross-ref against threat intel feed
}

function calculateRiskScore(signals: AuthRiskSignals): number {
  let score = 0
  if (signals.failedAttempts > 3)  score += 40
  if (signals.newDevice)           score += 20
  if (signals.newLocation)         score += 15
  if (signals.vpnDetected)         score += 10
  if (signals.torDetected)         score += 30
  if (signals.knownBadIp)          score += 50
  return Math.min(score, 100)
}

// Risk thresholds:
// 0–30:  Allow login normally
// 31–60: Require email OTP verification
// 61–80: Require SMS OTP verification + admin alert
// 81+:   Block login + lock account + notify user + admin alert
```

### 2.2 Account Lockout

- 5 failed login attempts → 15-minute lockout (Redis counter, TTL-based)
- 10 failed attempts in 1 hour → 24-hour lockout + email notification to account owner
- Lockout applies per account, not per IP (prevents account enumeration)
- Unlock path: email verification link (time-limited, single-use)

### 2.3 Suspicious Activity Monitoring

Automated alerts triggered for:
- Login from new country within 24 hours of previous login from UK
- Payout bank account changed + payout requested within 24 hours
- Multiple failed payment attempts (3+) in 1 hour
- Booking creation rate > 10 in 1 hour from one account
- Profile details changed (email, phone) + immediate financial action

### 2.4 Session Security

- JWT access tokens: 15-minute TTL (limits blast radius of stolen token)
- Refresh tokens: single-use rotation (compromised token detected immediately on reuse)
- Redis token blocklist: logout invalidates token server-side within 1 second
- Session binding: tokens include device fingerprint hash — stolen token from different device is rejected
- Concurrent session limit: 5 active sessions maximum per account

## 3. Identity Fraud & KYC Bypass Prevention

### 3.1 KYC Stack

```
Layer 1: Stripe Identity automated check
  • Document authenticity (holograms, MRZ, chip data)
  • Face match: selfie vs. document photo
  • Liveness detection: prevents photo spoofing
  • Database cross-reference: PEP/sanctions lists
  
Layer 2: Zipgrid manual review triggers
  • Document country does not match account registration country
  • Name on document does not fuzzy-match registered name
  • Document expiry < 3 months
  • Liveness confidence score < 90%
  • Prior failed verification attempts
  
Layer 3: Ongoing monitoring
  • Stripe Identity re-verification trigger: payout amount > £5,000 in 30 days
  • Admin flag: unusual payout patterns vs. session volume
  • Periodic re-verification: annually for all active hosts
```

### 3.2 Synthetic Identity Detection

Synthetic identities combine real and fake data. Detection signals:
- Email domain: disposable email addresses (blocked via disposable-email-domains list)
- Phone: VOIP numbers flagged (Twilio Lookup API)
- KYC document: same document used on multiple accounts → automatic flag + block
- IP: same IP used to create multiple accounts within 24 hours → investigation

### 3.3 AML Compliance

```
Transaction monitoring thresholds:
  • Cumulative payout > £10,000 in 90 days → enhanced due diligence review
  • Cumulative payout > £25,000 in 90 days → full AML review + possible SAR filing
  • Multiple transfers to different bank accounts in short succession → flag
  • Payout destination changes > 3 times in 90 days → flag

SAR (Suspicious Activity Report) filing:
  → National Crime Agency (NCA) via SARs Online
  → Do not notify the subject of the SAR (tipping-off offence)
  → Document the decision trail (file if uncertain)
```

## 4. Fake Listing Detection

### 4.1 Automated Checks at Listing Creation

```typescript
/**
 * @file listing-fraud-checks.ts
 * @description Automated fraud checks on listing creation.
 * Runs before listing enters manual review queue.
 */

async function runListingFraudChecks(listing: CreateListingInput, hostId: string): Promise<FraudCheckResult> {
  const checks = await Promise.all([

    // 1. Address verification — does this address exist?
    verifyAddressExists(listing.latitude, listing.longitude, listing.addressLine1),

    // 2. Duplicate detection — same OCPP chargePointId cannot be on two listings
    checkDuplicateOcppId(listing.ocppChargePointId),

    // 3. Same address, different host — possible sub-letting fraud
    checkAddressAlreadyListed(listing.latitude, listing.longitude),

    // 4. Host listing velocity — more than 3 listings created in 24 hours
    checkHostListingVelocity(hostId),

    // 5. Pricing sanity — price > 3× area median is suspicious
    checkPricingSanity(listing.pricePerKwhPence, listing.latitude, listing.longitude),

    // 6. Image analysis — detect stock photos, duplicate images across listings
    analyseListingPhotos(listing.photoUrls),

    // 7. OCPP connectivity — for smart chargers, verify it actually connects
    verifyOcppConnectivity(listing.ocppChargePointId),
  ])

  return aggregateResults(checks)
}
```

### 4.2 Ongoing Listing Monitoring

- **Zero booking fraud:** Listing active for 30 days with zero sessions → admin review. Real chargers get booked. Ghost listings are investigated.
- **Session completion rate:** If bookings start but sessions never complete (charger not responding) → flag + host contact + listing pause if pattern continues.
- **Review consistency:** If review content is inconsistent with session telemetry (no session data but positive review) → investigation.
- **Location drift:** Host changes listing location pin by > 500m → manual review required.

## 5. Chargeback Fraud Prevention

### 5.1 Session Evidence Package

Every completed session automatically generates an evidence package stored in S3/R2, referenced in Stripe dispute responses:

```
Session Evidence Package (auto-generated at session end):
├── OCPP transaction log (StartTransaction → MeterValues → StopTransaction)
├── Meter readings (start Wh, stop Wh, energy delivered kWh)
├── Session timeline (authorize_at, started_at, ended_at, duration)
├── Pricing snapshot (rate locked at booking, full cost calculation)
├── Device confirmation (charger brand, model, OCPP chargePointId)
├── Booking confirmation with driver acceptance timestamp
└── IP addresses and device fingerprint at booking time
```

When a Stripe dispute arrives:
1. Auto-pull evidence package from storage
2. Format as Stripe dispute response document
3. Submit within 24 hours (Stripe deadline: 7 days, but faster = higher win rate)
4. All within a Stripe webhook → automated dispute response system

### 5.2 Chargeback Risk Signals

Flag bookings for enhanced monitoring when:
- Driver account < 7 days old + first booking
- Driver has prior chargeback history (tracked in `driver_profiles.violation_count`)
- Booking value > £50 (above 95th percentile)
- Booking made from new device
- Payment method added in last 24 hours + immediate high-value booking

High-risk bookings: require host manual approval (instant book disabled automatically).

### 5.3 Chargeback SLA

| Stage | Action | Timeline |
|-------|--------|---------|
| Stripe dispute received | Webhook received → auto-pull evidence | < 1 minute (automated) |
| Evidence review | Trust & Safety reviews evidence package | < 4 hours |
| Response submitted to Stripe | Via Stripe dashboard API | < 24 hours |
| Outcome | Stripe decides within 60–90 days | Monitor + escalate if needed |

Target chargeback win rate: > 75% (industry average: ~40%).

## 6. Impersonation & Phishing Prevention

### 6.1 Zipgrid Will Never

This list is published in the app, knowledge base, and on-boarding:

```
Zipgrid will NEVER:
• Send you an email asking for your password
• Ask you to verify your account by clicking a link and entering your card details
• Send you a WhatsApp message asking for personal information
• Call you and ask for your OTP code
• Email from any domain other than @zipgrid.co.uk or @mail.zipgrid.co.uk
• Ask you to pay outside the app (e.g. via bank transfer)
• Ask a host to send charger access codes by email before a booking
```

### 6.2 Email Authentication (DMARC/DKIM/SPF)

```
DNS records (required for email deliverability and impersonation prevention):
  SPF:    v=spf1 include:sendgrid.net include:_spf.google.com ~all
  DKIM:   [SendGrid DKIM record] + [Google Workspace DKIM]
  DMARC:  v=DMARC1; p=reject; rua=mailto:dmarc@zipgrid.co.uk; pct=100

DMARC policy: p=reject — all unauthenticated emails claiming to be from @zipgrid.co.uk are rejected.
This blocks all email spoofing attacks.
```

### 6.3 Brand Impersonation Monitoring

- Google Alerts: "Zipgrid" — daily digest
- Trademark watch service: monitor for domain registrations similar to zipgrid.co.uk
- App store monitoring: check for fake "Zipgrid" apps (automated via AppFollow)
- Social media monitoring: flag accounts impersonating Zipgrid brand

**Response to impersonation:**
- Domain impersonation: UDRP complaint (uniform dispute resolution) + legal letter
- Fake app: App Store / Play Store takedown request within 24 hours
- Social impersonation: platform report + legal letter if persistent

## 7. Platform Abuse Detection

### 7.1 Promotional Abuse

**Referral fraud:**
- Same IP cannot create multiple accounts to self-refer
- Same device fingerprint cannot earn referral rewards twice
- Referral email domain must be unique (no `+` email tricks — normalised before check)
- Referral reward only triggers after referred user completes first real session

**Wallet abuse:**
- Wallet top-up then immediate refund pattern → flag + freeze
- Chargeback on wallet top-up → balance removed + account investigated

### 7.2 Fake Reviews

```
Review manipulation detection:
  1. IP match: reviewer and reviewee accessed from same IP → flag
  2. Device match: same device used for both accounts → flag
  3. Velocity: account created < 7 days ago posting 5-star reviews → held for review
  4. Pattern: sudden cluster of 5-star reviews for one listing (> 5 in 24 hours) → flag
  5. Content analysis: AI checks for templated or bot-generated review text
  6. Session requirement: review rejected if no confirmed session exists for that booking
```

### 7.3 API Abuse & DDoS

```
Rate limiting (Upstash Redis):
  • Authenticated users:  100 req/min
  • Unauthenticated:      20 req/min
  • Geo-search endpoint:  30 req/min (expensive PostGIS query)
  • Auth endpoints:       5 req/min per IP

Cloudflare:
  • Layer 7 DDoS protection (automatic)
  • Rate limiting rules mirroring API limits
  • Bot management: blocks automated scraping
  • Turnstile on all auth forms

OCPP:
  • 10 messages/second per chargePointId
  • Charger disconnected if rate exceeded
```

## 8. Incident Response for Fraud Events

```
Fraud detected (automated or reported)
        │
        ▼
Immediate containment (< 15 minutes):
  • Suspend affected account(s)
  • Freeze pending payouts
  • Invalidate all active sessions and tokens
  • Preserve evidence (do not delete logs)
        │
        ▼
Investigation (< 24 hours):
  • Review full account history
  • Cross-reference with known patterns
  • Assess financial exposure
  • Determine scope (isolated or pattern)
        │
        ├── Isolated incident
        │         ▼
        │   Resolve + inform affected parties
        │   + improve detection rule
        │
        └── Systemic pattern
                  ▼
            Engage legal counsel
            Consider law enforcement referral
            Platform-wide defensive measure deployed
            Board notification if > £10,000 exposure
```
